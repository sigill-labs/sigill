# @fidant/e2e

End-to-end tests on the local stack, with a leak detector that checks every test. The rules it enforces are in [docs/decisions/0001](../../docs/decisions/0001-e2e-tests-and-leak-model.md).

## Running

```sh
pnpm --filter @fidant/e2e exec playwright install chromium  # once per machine
pnpm e2e                                                    # from the repository root
```

`pnpm e2e` builds the web client, starts coturn, Mailpit and the server on free ports, runs the specs in `tests/` and stops them. `pnpm check` does not run it.

The specs run in Chromium. To run them in other engines, install those once with `pnpm --filter @fidant/e2e exec playwright install firefox webkit` and name one engine in `FIDANT_E2E_BROWSER`, `chromium`, `firefox` or `webkit`: `FIDANT_E2E_BROWSER=firefox pnpm e2e`. Run one engine per invocation, because the server respawned after the restart tests keeps its 60 s warm-up (`STARTING_MS`), which the next engine's early tests would hit. Each engine is a Playwright project of its own, so test results, observations and canaries carry its name. A list or an unknown name stops the run, and so does any engine but Chromium with `pnpm e2e:networks`. `.github/workflows/nightly.yml` runs Chromium, Firefox and WebKit, one job per engine, as a user that can only reach loopback (see [The nightly's loopback-only user](#the-nightlys-loopback-only-user)), every night and on a pull request that changes that file; every other pull request runs Chromium only.

coturn is the TURN relay (`brew install coturn` on macOS, the `coturn` package on Linux). It listens on 127.0.0.1 only. The stack makes a relay master for the run and a relay list of two relays on that coturn, each with its own RSA key pair: `bad`, whose secret coturn doesn't know, and `loc`, whose secret, derived from the master, coturn has. The server gets the list and the master as `RELAYS_FILE` and `RELAY_MASTER_FILE`, checks both relays, shows `bad` down and `loc` up at `/relay-status`, and the `joined` signaling message hands each paired browser credentials for `loc`. The server also gets `TURN_URLS` and `TURN_SECRET_FILE`, `loc`'s URLs and secret, which it ignores while it has a list. Without `turnserver` on PATH the stack starts without it and `joined` carries no ICE servers; with `CI` set, that fails the run instead. Global setup sets `FIDANT_E2E_TURN_URLS` only when coturn runs, so a spec that needs the relay can skip on it, and `FIDANT_E2E_RELAYS_FILE` and `FIDANT_E2E_RELAY_MASTER_FILE` to the files' paths, with each relay's private key next to the list as `<id>.key`.

Mailpit catches the server's mail (`brew install mailpit` on macOS, the release binary on Linux). Its SMTP and HTTP API listen on 127.0.0.1 only, on two free ports, and it never sends mail on. The server gets `MAIL_ENABLED=1`, `MAIL_SMTP_URL`, `MAIL_FROM` and `PUBLIC_ORIGIN` (its own `https://localhost:<port>`), so `hello` says mail is on and emailed links point at the stack. Without `mailpit` on PATH the stack starts without mail; with `CI` set, that fails the run instead. Global setup sets `FIDANT_E2E_MAILPIT` to the API's URL only when Mailpit runs, so an email spec can skip on it. Its output (errors only) goes to `observations/run/mailpit.log`. `pnpm e2e:networks` runs no Mailpit.

## Large files

```sh
FIDANT_E2E_LARGE=1 pnpm e2e  # from the repository root; Chromium only
```

`tests/large-files.spec.ts` sends a 1 GB and a 5 GB canary and skips unless `FIDANT_E2E_LARGE` is `1` and the engine is Chromium. `nightly.yml` sets it in its Chromium job. Each canary is written to the system's temporary directory a MiB at a time and chosen by its path, so it needs about 5 GB free there; the 1 GB one is deleted before the 5 GB one is written. The recipient saves into `fakeSavePicker`, a save dialog stub that counts the bytes it is given and keeps none. Each test passes only if the stub got exactly the file's size, both pages show the SHA-256 that Node computed while writing the canary, the sender's page says it was delivered, and the summed RSS of the browser's processes grew by less than 1 GiB from just before Download (`src/rss.ts`). It logs the rate in MB/s and the RSS. The leak check searches only a large file's sampled bytes: the first and last MiB and one MiB at every 64 MiB, each sample on its own, and the SHA-256 of the whole file ([decision 0027](../../docs/decisions/0027-nightly-large-files-and-egress-block.md)).

## A lost signaling socket

`tests/takeover.spec.ts` has three tests, one for the recipient, one for the sender and one for the recipient whose route stalls before its page sees the socket close (the repeated `join` goes onto the silent socket and is swallowed, then the `resume` answer sends it again), of a page that loses its signaling socket mid-transfer and takes its attempt back with its resume token ([decision 0033](../../docs/decisions/0033-signal-socket-takeover.md)). It simulates both drops on one machine, with two fixtures from `src/fixtures.ts`. `cuttableSignal(page)` routes the page's `/signal` sockets through Playwright's `routeWebSocket`; its `cut()` closes the page's side of the first socket with 1006, while the server's side stays open and hears nothing more, as on a lost network, and `serverClosedAt()` says when the server ended it. `silence()` makes the socket stop passing frames while it still looks open, and `swallowed()` lists the types of the frames it took. `breakableRoute`, an init script, makes each page's connection report `disconnected` and queues what its data channels send until an ICE restart has completed, so the route recovery of [decision 0031](../../docs/decisions/0031-ice-restart-recovery.md) has to run. The server therefore sees the takeover of a socket that is still open; the hold after a close with no close frame is covered by the unit tests in `apps/server/src/signaling.test.ts`. `a public address that changes mid-transfer` in `pnpm e2e:networks` is the real case (see below). To run it alone, run `pnpm build` from the repository root, then `pnpm exec playwright test tests/takeover.spec.ts` from `apps/e2e`.

## Network scenarios

```sh
pnpm e2e:networks  # from the repository root; needs Docker with Compose v2
```

`pnpm e2e:networks` runs only `tests/networks.spec.ts`. Global setup starts `networks/compose.yaml`: two sites behind NAT routers (`networks/router.sh`), a browser container per site address running `playwright run-server` (a1 and a2 at site A, b1 at site B, published on 127.0.0.1:39011, 39012 and 39021), and coturn at 198.51.100.20 on the public network, which has no way out. coturn also serves TURN over TLS on 443 as `turn.fidant.test`, which the browsers resolve to its address, with a self-signed certificate made for the run. Chrome checks TURN certificates despite `ignoreHTTPSErrors`, so the browsers trust that certificate's public key with `--ignore-certificate-errors-spki-list`. The server runs in its own container at 198.51.100.10 on that network, so the browsers reach it through their routers. It reads a relay list (`RELAYS_FILE`) and a relay master (`RELAY_MASTER_FILE`) made for the run: `net`, coturn, which runs with net's secret derived from the master, then `sto`, the relay box. It offers the first relay its check finds up, so the rows use `net`. It listens on 443, the one port router mode `tcp-443` lets out, so the browsers get `https://198.51.100.10` as their base URL. The host never connects to it. On Docker Desktop the host cannot reach 198.51.100.x at all, and does not need to.

One run at a time per machine: every checkout's run uses the same compose project, container and network names, subnets and host ports, and setup removes the containers it finds. So global setup first looks for another checkout's run with `docker compose ls --all`. While one is running, it waits, checking every 10 s and printing a line naming that checkout's compose file every 30 s, and starts once that run's containers are gone. It gives up after 15 minutes. A run that left only stopped containers is dead and never clears, so when setup sees that on two checks in a row, it fails and prints the command that removes them: `docker rm -f fidant-e2e-server; docker compose -p fidant-e2e down --remove-orphans`. A run of the same checkout removes leftovers of its own killed runs as before. A run that is still building its images has no containers yet, so two runs started within the same minute or so, or two waiting for the same run, can both go ahead.

The public network also holds the box at 198.51.100.30 (`networks/box`): Ubuntu 24.04 with systemd, running the app server, HAProxy, Caddy, coturn and rsyslog as on the POC box, configured from the rendered `apps/infra/box/user-data.sh` (`src/stack/box.ts`). The browsers reach it as `https://fidant.se` and `turn.fidant.se` through `--host-resolver-rules`. The `the box` test sends one file through its relay, then reads its journal and `/var/log/syslog`: nothing from the four services may reach syslog, journald's settings must resolve to `ForwardToSyslog=no`, `MaxRetentionSec=29day` and `MaxFileSec=1day`, and the app server's journal lines must pass the stdout allowlist and hold no client address or user agent. Every run builds the five images in `networks/` (the tools, box, relay, coturn and alb), the box's `node` stage for pages, and the signaling image, so a Dockerfile change takes effect without a new tag; Docker's layer cache makes an unchanged build take seconds. A CI runner starts with no layers, so CI's `e2e-networks` job sets `FIDANT_E2E_GHA_CACHE`, which adds `networks/compose.gha-cache.yaml`: each image's layers go to GitHub Actions' cache under their own scope, and a run with them cached builds in about 25 seconds instead of 2.5 to 4.5 minutes. Their base images are pinned by digest, and Dependabot proposes updates for all but alb's and the signaling image's, which it doesn't watch yet. The box Dockerfile's `node` stage is also the server container's image, and `src/stack/box.test.ts` fails when its major differs from `.node-version`. The browser containers' Playwright image has a tag but no digest, because its tag follows `@playwright/test` in the lockfile.

The relay box is at 198.51.100.40 (`networks/relay`): Ubuntu 24.04 with systemd and the packages that `apps/infra/relay/install.sh` would install, so the script runs offline at boot, as on a new server. It gets the script's inputs and the run's TURN certificate, in place of a Let's Encrypt one, from `FIDANT_E2E_RELAY_DIR`. The browsers reach it as `sto.relay.fidant.test`. Its `APP_URL` is the server's `https://198.51.100.10`, whose self-signed certificate it doesn't trust, so its timer's fetch gets no secret. The `the relay box` tests check what the script set up, that the relay answers STUN and refuses every allocation while it has no secret, and that its fetch, with the server's certificate pinned, applies sto's secret from the server's hand-out, after which the server finds sto up.

The public network also holds `alb` at 198.51.100.50 (`networks/alb`), nginx standing in for the AWS load balancer in front of the hosted signaling container (decision 0023). It ends TLS with the run's TURN certificate, keeps idle connections from clients for 120 seconds (only between clients and the stand-in: it sends `Connection: close` upstream on requests that are not upgrades and keeps no connections to the server, so the suite does not exercise `HTTP_KEEP_ALIVE_MS`), appends the address it sees to `X-Forwarded-For` and passes everything, WebSockets included, to `signal` at 10.89.3.10. `signal` runs the image that `apps/server/Dockerfile` builds, as the hosted task will run it: a read-only root with one tmpfs at `/run/fidant`, no healthcheck, `SIGNALING_ONLY=1`, `PUBLIC_ORIGIN=https://fidant.se`, `TRUSTED_PROXIES` set to the internal `lb` network it shares only with `alb`, `STUN_URLS`, `HTTP_KEEP_ALIVE_MS=125000`, a relay list of `net` alone and the run's relay master as `RELAY_MASTER`, which the image's entrypoint writes to `RELAY_MASTER_FILE`. It has no route to coturn, so `/relay-status` shows `net` down. The image builds from the repository on every run, so a change to the root `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml`, `apps/server/package.json` or `packages/protocol/package.json`, which the Dockerfile copies before its install layer, needs the internet once. The `the signaling image` tests connect to it from Node in the browser containers, with the `ws` package from `apps/server`, so `alb` appends the routers' addresses, and they read the container's log into `observations/run/signal.log`.

The public network also holds `pages` at 198.51.100.60 (`networks/pages`), standing in for the CDN in front of the pages (decision 0023). `serve.ts` answers each request through `src/edge.ts`, which runs `apps/infra/edge/site.js` on the request as CloudFront does, reads the object it names from a web build made for the run with `SIGNALS_FILE=signals.json`, as the release uploads it with the upload's cache rule, and runs the function again on the response. A missing object gets S3's bare 404, other methods CloudFront's 403. It passes `/relay-secret/<id>` on to `alb` as the distribution passes it to the signaling name, and answers 404 for any other URI the guard sees, one that contains `/relay-secret/` once its escapes are decoded and its backslashes read as slashes, as the function does (decision 0023 cites why). It runs on the box Dockerfile's `node` stage, serves the run's TURN certificate, whose names include `fidant.se` and `sto.signal.fidant.se`, and writes nothing. The browsers resolve `sto.signal.fidant.se` to `alb`, and `fidant.se` to the box, except where a test sets `hostRules`: the `pages from the edge function` test maps `fidant.se` to `pages`, so its pages have the origin `https://fidant.se`, which the image's `PUBLIC_ORIGIN` accepts, and open their WebSocket on the image's name. It sends one file directly, reads the image's log into `observations/run/signal.log` again, and checks that `https://fidant.se/signal` answers 404 and that `pages` passes the relay's hand-out on. Each run builds the web client twice: `apps/web/dist`, the same-origin build that the server container and the box serve, and the pages build in a temporary directory.

Each row of the spec's table names the sender's and recipient's site, the mode of router-b (`routerMode()` in `src/stack/networks.ts`) and the candidate pair ICE must select. The `same network` row also captures every packet on router-a's outside interface during the transfer (`captureEdge("router-a")`) and fails on any packet but TCP to the server's 443 and STUN Binding messages to coturn's 3478, apart from ARP and link-scope IPv6 multicast (ff02::/16), which stay on the link, so no peer-to-peer traffic, and no TURN traffic, left site A. What reaches the server is the leak scan's to check.

The `a route cut mid-transfer` test is the recovery of [decision 0031](../../docs/decisions/0031-ice-restart-recovery.md). It sends 1 MiB over the `lossy` link from a sender who refuses the relay, and once bytes have arrived it drops all UDP between site B and router-a (`cutRoute()`, `router.sh cut`), which leaves signaling and coturn's STUN reachable. It restores the route (`restoreRoute()`) as soon as the recipient's recorded frames show its second `join`, in a `finally`, because the routers are shared across the run. It passes only if the file arrives verified with a matching SHA-256, the recipient's progress never goes back, each page made one `RTCPeerConnection` whose local ICE password differs after the cut, every `join` the recipient sent is the same message, and the sender shows no interrupted transfer. The `a public address that changes mid-transfer` test is the real case of [decision 0033](../../docs/decisions/0033-signal-socket-takeover.md). It runs on the pages of the edge function, so the recipient's socket goes through `alb`, and sends 1 MiB over the `lossy` link from a sender who refuses the relay. Once bytes have arrived it moves router-b from 198.51.100.3 to 198.51.100.4 and flushes its conntrack table (`renumberSiteB()`, `router.sh renumber`), so b1's open socket and its peer-to-peer flow go on from the new address, where nothing expects them. It captures router-b's edge meanwhile (`captureEdge("router-b")`) and checks that `alb` answered the old socket with a reset to the new address, and that signaling and the peer-to-peer flow then left from it. It passes only if the recipient opened a second socket and sent one `resume`, the file arrives verified with no "Try again", each page made one `RTCPeerConnection` whose ICE password changed, every message names one attempt, and the resume tokens appear only in `resume` frames and never in the signaling log. It gives router-b its address back (`restoreSiteB()`) in a `finally`.

Teardown removes every container and network, also after a failed run; a run that was killed is cleaned up by the next one. The first run pulls the images, so it needs the internet once.

## Writing a test

Import `test` and `expect` from `src/fixtures.ts`, not from `@playwright/test`.

- The default `page` and `context` are recorded as the actor `default`. For more browsers, call `actor("sender")`, `actor("recipient")` and so on. Each gets its own context and page and its own observations file. Do not call `browser.newContext()`: an unrecorded context fails the test.
- `test.use({ remoteBrowsers: { sender: "ws://127.0.0.1:39011/" } })` opens that actor in a browser served by `playwright run-server` at the endpoint, with the project's launch options and the same recording. Start the server with `--unsafe`, or it drops the launch `args`. Downloads from a remote browser have no local `path()`; use `saveAs()` or `createReadStream()`.
- `test.use({ hostRules: "MAP fidant.se 198.51.100.60" })` puts rules before the project's `--host-resolver-rules` in that test's remote browsers, where the first match wins. Playwright refuses `launchOptions` in a describe group, because a worker option forces a new worker.
- `canary` gives random bytes from the run seed and the test's title. Fork it per canary: `canaryFile(canary.fork("file"))`, `canaryKey(canary.fork("key"))`.
- `leaks.watch(file, label?)` registers a canary file and returns it: its bytes and their SHA-256, the tokens in its name and type, the SHA-256 of its name, and its size. `leaks.watchKey(label, key)` registers a key, as bytes or as text such as a fragment secret: the text, every byte value its hex, base64url or base64 decodes to, and the SHA-256 of each byte value and of each text form (as given, base64url, base64 and hex, also after a `#`). `leaks.watchText(label, text)` registers other text that must not appear whole, such as a recipient name. `leaks.watchContent(label, text)` registers text that is content, such as a text shared from `/send/secret`: any 16 bytes in a row of its UTF-8, and its SHA-256.
- An emailed link's secret, the sender's typed name, the address, the server's value and the token may appear in a few places ([decision 0012](../../docs/decisions/0012-email-recipients.md)). Pass those places as the last argument of `watchKey` or `watchText` (`Allowed` in `src/leaks/needles.ts`): the signaling messages about the link that may carry it, such as `sent email` (the first one only) or `received token`, and the mail to the address that may carry it, either the body of the notice (by its Mailpit ID) or any part of any mail to it. A mail counts only if it is one plain-text part to that address alone: one To, no Cc or Bcc. Findings anywhere else stand, a second copy of the notice and the headers of the notice itself included.
- After the test, the detector scans what the test observed for every secret it registered and fails the test on any finding. `leaks.scan()` returns the findings so far without failing, and `leaks.check()` returns the report the teardown would throw (undefined when clean). A test that leaks on purpose calls `leaks.expectLeaks()`. `tests/leaks.spec.ts` shows a leak caught in a request URL, a request header, a request body (plain and gzip), a sent websocket frame and a console message. The unit tests in `src/leaks/` cover each encoding, hash, window and size rule.
- Once all tests are done, a run-level sweep scans every observation against every secret of the run, so a leak that shows up in another test's traffic or a later log line still fails the run.

- `restartServer()` from `src/stack/server.ts` restarts the server on the same port and resolves once it listens again, like a deploy or a crash: browsers lose their signaling sockets and the server forgets every link. Global setup's server service does the restart (it starts the server again whenever it exits on SIGTERM), and both runs write to the same logs, so the leak checks cover them. The specs run one at a time (`workers: 1`), so a restart cannot break another test. Local stack only: `pnpm e2e:networks` has no restart.
- Every recorded context logs, as `fidant-e2e:` console warnings, the error of a rejected `createOffer`, `createAnswer`, `setLocalDescription`, `setRemoteDescription` or `addIceCandidate` call on a peer connection and the call stack of every `close()` on a peer connection or data channel, which the app keeps out of its own console. The recorder writes them to the observations, so a failed CI run says why a connection ended. The script runs before any test script, so a test that assigns its own replacement for one of these methods overwrites the logging wrapper, and its injected failures are not logged. A test that wraps a method and calls the original still goes through the logger.

Requests outside the stack are aborted and fail the test. A test may still route the stack's own sockets with `page.routeWebSocket`, as `tamperSignal` in `tests/hostile-path.spec.ts` does to alter signaling: a page route takes precedence over the recorder's context route and bypasses its off-stack block for every URL it matches. Match only stack URLs. The recorder still sees the frames on the wire, as the server sends and receives them (what the page sends after the edit, what the server sends before it).

### The nightly's loopback-only user

Each job of `.github/workflows/nightly.yml` builds as `runner`, then runs Playwright from `node_modules/.bin`, not through pnpm, as `fidant-e2e`, a user the job creates with access to the checkout and write access to `apps/e2e` itself. Global setup starts coturn, Mailpit and the server as that user too. Rules in `iptables` and `ip6tables` let it send through `lo` only, which also carries packets to the runner's own addresses, so ICE host candidates still connect. The job first maps the machine's own names to 127.0.1.1 in `/etc/hosts` where the runner image left them out. It then removes every nameserver off loopback from `/etc/resolv.conf`, and fails if none is left. Some runners list `168.63.129.16` after two loopback nameservers, and a lookup refused at both went on to it and left loopback: run 45986710828's WebKit leg sent 440 such packets, all refused, and failed. Every name lookup to a loopback port 53 goes to the chain `fidant-e2e-dns`, and every other packet it sends to `fidant-e2e-egress`. Each chain logs the packet with its own name as the prefix and refuses it. Before the tests, `curl http://1.1.1.1/`, `getent hosts example.com` and `curl 'http://[::1]:53/'` must fail as the user and be logged, and the lookup must log nothing in `fidant-e2e-egress`. After them, the job prints the kernel's lines and fails if `fidant-e2e-egress` logged anything, background traffic of a browser included, or if `fidant-e2e-dns` did on the Chromium or Firefox leg. On the WebKit leg it only warns about lookups, which are WebKit resolving the other peer's mDNS candidate names. [Decision 0027](../../docs/decisions/0027-nightly-large-files-and-egress-block.md)'s runbook says how to read them and how to dispatch the workflow by hand. A night that isn't for a pull request and fails, runs out of time or is cancelled comments on the open issue titled "Nightly failed" that the Actions bot opened, or opens one.

## What is scanned

Today:

- Browser requests and responses: URL, headers and request bodies. WebKit omits the Cookie header from `allHeaders()`, so the recorder adds the cookies the context holds for the URL. WebKit leaves the bytes of a Blob or File out of a body, and no engine exposes a streamed one, so the recorder marks a request `bodyMissing` when its `Content-Type` starts with `multipart/form-data` or its exposed bytes contain `content-disposition: form-data` (any case), and any request with no exposed body unless it is a GET, a HEAD, a CORS preflight (an OPTIONS with `Access-Control-Request-Method`) or says `content-length: 0`. The scan reports `bodyMissing` as a limit and the test fails. Gaps: no engine shows the recorder the headers of a WebSocket upgrade, `/signal` included, so a cookie sent only with the upgrade, or a subprotocol the page names, is not scanned. Firefox and WebKit record no request that a page sends while its context closes, such as a `keepalive` fetch on `pagehide`, or in Firefox a beacon.
- WebSocket frames, sent and received, including `/signal`.
- Browser console messages: the text and the page URL without its fragment.
- Server stdout and stderr. Stdout must also pass a strict allowlist: one JSON object per line, with known keys and values only (`src/leaks/server-log.ts`).
- coturn's verbose log, `observations/run/coturn.log`, Mailpit's output, `observations/run/mailpit.log`, and the stack's own events, such as an unexpected server exit, `observations/run/stack-events.log`.
- Every mail Mailpit caught, as two captures of its raw source: the headers, unfolded, which carry the envelope as Mailpit records it (Return-Path, Received and, for a recipient not in To or Cc, Bcc), and the body. A finding names the part, such as `observations/<test>/mail/<ID>.eml body`. Each test's check saves the mail that arrived during the test to `observations/<test>/mail/<ID>.eml`, and its teardown deletes those messages from Mailpit. Global teardown saves what is left to `observations/run/mail/`.
- In the network scenarios only, every packet to and from coturn, `observations/run/coturn.pcap`. The `pcap` service of `networks/compose.yaml` runs tcpdump in coturn's network namespace with `NET_RAW`, so no sudo is needed (decision 0001 expected sudo on CI). The file is scanned as raw bytes, one capture per test from where it stood when the test began. It holds STUN and TURN headers, DTLS ciphertext and, for TURN over TLS, TLS ciphertext only, so it is safe as a CI artifact. `pnpm e2e` has no packet capture.
- In the network scenarios only, the signaling image's container log, stdout and stderr (`observations/run/signal.log`), written by the `the signaling image` tests.
- In the network scenarios only, the box's journal for fidant, haproxy, caddy and coturn (`observations/run/box-journal.jsonl`, the message of each `journalctl -o json --all` entry, one per line, binary ones hex-encoded) and its `/var/log/syslog` (`observations/run/box-syslog.log`), written by the `the box` test after its transfer.

Every capture is decoded into views (percent, JSON escapes, base64, hex, gzip and others, nested) before matching, so encoded leaks are caught too.

## Adding an observation point

Write the raw data under `observations/`. The run-level sweep fails on any file there that no leak check reads, naming it, so every new file needs one of these:

- A file for the whole run, directly in `observations/run/`: add it to `runSources` in `src/paths.ts`, read as `lines` (a log, one capture per line) or `binary` (raw bytes, such as a packet capture). Both the per-test scan in `src/leak-watch.ts`, which reads what the file grew by during the test, and the sweep in `src/sweep.ts`, which reads all of it, then pick it up. A file that holds nothing a test could leak, such as `server.pid`, goes in as `ignored` with its reason.
- A file per test, in `observations/<test>/`: turn what the point saw into `Capture`s (`src/leaks/scan.ts`), a `point` naming where it was seen, such as `observations/<test>/mail/<ID>.eml`, and the `bytes`, with a `contentEncoding` hint if the bytes are compressed. Add them to the per-test scan in `src/leak-watch.ts`, and add a rule for the file to `formatOf` in `src/sweep.ts`. `src/leaks/captures.ts` does this for browser records (`<actor>.jsonl`) and saved mail (`mail/<ID>.eml`).

## Reproducing a failure

The run prints its seed first:

```
Canary seed: 9d46…d665 (set FIDANT_E2E_SEED to replay it)
```

A failure repeats the seed. Run `FIDANT_E2E_SEED=<seed> pnpm e2e` to get the same canaries.

## Findings are public

A finding prints up to 64 bytes around the match, and `observations/` is uploaded by CI. Both are public. That is acceptable only because canaries and canary keys are throwaway test values. Saved mail is uploaded too: it holds links to the local stack with throwaway keys, and made-up addresses. Never watch real data, real keys or anything else secret.
