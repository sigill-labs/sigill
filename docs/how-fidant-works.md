# How Fidant works

This is the source of truth for how Fidant moves a file or a shared secret and why no infrastructure can read it, except through a peer-to-peer link that Fidant emails (see "Emailed links"), which is off until verified transfers need it. It describes the code on `main` today. The site at fidant.se runs the `production` branch, which `.github/workflows/promote.yml` moves forward to each merge on `main` (`docs/decisions/0026-auto-promote.md`), or a maintainer does by hand. The box builds only a commit on `main`'s first-parent history. The site can run an older commit than this describes for the minutes a deploy takes, or longer after a failed run (`docs/decisions/0020-deploy-from-production.md`). Planned work is marked as planned.

A change to security or data flow updates this document in the same pull request, and then the web pages that explain it (see "Keeping this true" at the end).

## Parts

| Part                  | Where                                                                                     | What it does                                                                                                                                                                                                                                    |
| --------------------- | ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Web app               | `apps/web`, runs in each browser                                                          | Creates links and keys, encrypts and decrypts, checks the file. All cryptography happens here.                                                                                                                                                  |
| Server                | `apps/server`, the box at fidant.se                                                       | Serves the web app over HTTPS, passes setup messages between browsers on the `/signal` WebSocket, checks the relays and hands each relay its secret, and, when mail is turned on, emails links and codes.                                       |
| Relay (STUN and TURN) | coturn on the relay box at `sto.relay.fidant.se`, set up by `apps/infra/relay/install.sh` | Tells browsers their public address (STUN) and, if the sender allows it, carries encrypted traffic when they haven't connected directly 3 s after the sender applies the recipient's answer (TURN), while it is available. See "The relay box". |
| Fallback relay        | coturn at `turn.fidant.se`, on the box                                                    | The same, but offered only when the server has no relay list (see "The relay box").                                                                                                                                                             |
| Front proxy           | HAProxy, on the box                                                                       | Holds TCP port 443 and hands each connection on by its TLS server name, without decrypting it.                                                                                                                                                  |
| Shared protocol       | `packages/protocol`                                                                       | Signaling message types, parsers and limits used by both the server and the web app.                                                                                                                                                            |
| Mail service          | SMTP, from `apps/server/src/mail.ts`                                                      | Delivers the emails the server sends for emailed links, which are off. Mailpit locally; see "Emailed links" for production.                                                                                                                     |

The box is an AWS Lightsail instance in Stockholm (eu-north-1), and so is the relay box. There are no accounts, no file storage and no database of people or transfers. The server holds what it knows about pages and transfers only in memory. Among the secrets it keeps on disk is the relay master, and the relay box keeps its own secrets in a small database file (see "The relay box").

## Modes

Three independent choices set how a transfer runs. Every combination uses the same keys, frames and checks.

| Choice                                | Modes                                                                                                                                                                                                                          | Details                                      |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------- |
| What is sent                          | A file (`/send/file`), or a shared secret the sender types or pastes (`/send/secret`)                                                                                                                                          | "The transfer", "Sharing a secret"           |
| How the link reaches the recipient    | The sender copies the link and passes it on over any channel they choose, and the secret never leaves the browser; or, while email is on, the sender gives an email address and our server emails the link and a one-time code | "The link", "Emailed links"                  |
| The route the encrypted traffic takes | Direct over local addresses, direct through public addresses learned from STUN, or through our TURN relay; the sender can refuse the relay for a send                                                                          | "How the file travels", "Refusing the relay" |

Emailing a link is offered only when the server has a mail service and `MAIL_ENABLED=1` (see "The mail service"), and it is the one mode in which a link's secret reaches our server.

## The link

`apps/web/src/lib/link.ts`

For each recipient the sender's browser creates a link:

```
https://fidant.se/r/<link ID>#<secret>
```

- **Link ID**: 16 random bytes, base64url (22 characters). The server sees it and uses it only to pair the two browsers.
- **Secret**: 32 random bytes, base64url (43 characters), in the URL fragment. Browsers don't send the fragment to servers, and the site sets `Referrer-Policy: no-referrer`. The app sends the secret nowhere except in the one message that asks our server to email that link (see "Emailed links"); apart from that it only derives keys from it. The router reads the fragment on `/how`, where it is a section anchor, and on the receive page, where it keeps the page's first address, fragment included, in memory only. That lets the "Go back to it" bar return to an unfinished transfer: the link it shows carries only the path, and following it puts the secret back in the address bar and the session history. On other pages, switching language (and back or forward after a switch) and the pre-paint script carry the fragment unchanged into the new address in the same tab; on a receive link neither changes the address or reads the fragment. Nothing more reaches the server.

Both come from `crypto.getRandomValues`. Every recipient gets their own link ID and secret. A link Fidant emails carries a marked fragment, `#e.<value>.<secret>` (see "Emailed links").

## Keys

`apps/web/src/lib/keys.ts`

Two keys are derived from the secret with HKDF-SHA-256. Both are AES-256-GCM `CryptoKey`s, non-extractable, usable only to encrypt and decrypt.

| Key        | HKDF salt                                                          | HKDF info          | Protects                     |
| ---------- | ------------------------------------------------------------------ | ------------------ | ---------------------------- |
| Signal key | the link ID's 16 bytes                                             | `fidant/v1/signal` | setup messages (SDP and ICE) |
| File key   | the transfer ID (16 bytes) ‖ the recipient's attempt ID (16 bytes) | `fidant/v2/file`   | every frame after INIT       |

Each side puts a fresh random value of its own into the file key's salt: the sender a new transfer ID for every attempt, sent in INIT, and the recipient a new attempt ID for every attempt, which the sender learns from `joined`. A `join` the recipient sends again on the same socket carries the same ID and makes no new key: the attempt, its connection and its frame numbers go on (see "Recovering a dropped route"). Both sides number their frames from 0 in every attempt, so each needs a key it has never used: a retry gets one from the new transfer ID, and a recipient shown an INIT replayed from an earlier attempt gets one from its new attempt ID. So no (file key, nonce) pair is ever used twice. A retry that continues a dropped file is such an attempt too, with its own key and frames numbered from 0; only its CHUNKs start partway through the file (see "Continuing after a drop"). Before frame version 3 the salt was the transfer ID alone, and a replayed INIT made the recipient seal its first frame twice under one key and nonce (FID-231, `docs/decisions/0017-protocol-audit-fixes.md`).

## Connecting the two browsers

`apps/web/src/lib/peer.ts`, `apps/web/src/lib/signaling-client.ts`, `apps/server/src/signaling.ts`, `packages/protocol/src/signaling.ts`

```
server    → each page  hello {mail}
sender    → server     host {links, turn}
recipient → server     join {link, attempt}                 with a token on an emailed link
server    → both       joined {link, attempt, iceServers, turn}
both                   relay seal({ice, version marker})   each page's first signal
recipient → sender     relay seal_r({commit, hash})         hash of its DTLS fingerprint
sender    → recipient  relay seal_s({offer, sdp, check})    only after the commit
recipient → sender     relay seal_r({answer, sdp})          its fingerprint must match the commit
both                   relay seal({ice, candidate})        trickle
sender    → recipient  relay seal_s({restart-offer, sdp})  only when adding the relay, then trickle again
recipient → sender     relay seal_r({restart-answer, sdp})
sender ⇄ recipient     WebRTC data channel "fidant" opens
recipient → server     join {link, attempt}                 the same again, only when its open connection drops
```

- On connect the server sends `hello`, saying whether it can send mail. Only then does the send page offer to email a link, and only as an opt-in (see "Emailed links").
- The sender's page registers its link IDs with `host`, along with whether it allows our relay (`turn`). Anyone can host a link ID nobody hosts. A link ID another socket already hosts is left out of the message as if it weren't there: the server hosts the others and answers `error` with `already-hosted`, and the page sends its whole list again 5 s later (`REHOST_AFTER_MS`), so the link is hosted once the other socket lets it go. One taken link ID never blocks a sender's other links.
- The recipient's page joins with the link ID and an attempt ID: random, new for each page load, each "Try again" and each automatic retry on a new socket. A `join` it sends again on the same socket carries the same attempt ID: after `refused` with `starting` (below), and when its open connection drops (see "Recovering a dropped route").
- The server binds at most one recipient page to a link and sends `joined` to both. A `join` from the socket already bound to that link, with the same attempt ID, is a repeated join: the server runs the same checks and sends a new `joined` to both, with ICE servers made at that moment (see "Recovering a dropped route"). Any other `join` on a bound socket gets `error` with `already-joined`. It keeps no record of used links. The sender's page decides and answers with `refuse` (`used`, `busy`, `unknown` or `drop`). The server itself refuses a second recipient page with `busy`, as it does a join past the link's 10 pairings per 30-second window, a repeated join included, and a link nobody hosts with `unknown`, or with `starting` during the first 60 s after it starts (`STARTING_MS`, decision 0018), when the link's sender may not have hosted it again yet.
- Every commit, SDP and ICE message is sealed with the signal key: `base64url(iv(12) ‖ AES-GCM ciphertext ‖ tag(16))` with the additional data `fidant/v1/signal|<link ID>|<attempt>|<direction>`. The server can't read or change them, can't reflect a message to its sender, can't move it to another link, and can't replay it into another attempt. All of this rests on the server not having the secret, which holds for every link except one Fidant emails.
- Each page's first sealed signal is its version marker: an `ice` message whose candidate is empty, whose `sdpMid` and `sdpMLineIndex` are null and whose `usernameFragment` is `fidant-v<n>`, with n the page's frame version (`FRAME_VERSION` in `frames.ts`, see "Frames"). The sender reads the recipient's version before it makes the offer, and the recipient reads the sender's before it answers. A page that sends no marker counts as version 3, so a page with the check, which runs version 4, makes no offer or answer for it. A marker counts only before the commit (on the sender's side) or the offer (on the recipient's); a later or a second one is dropped like a candidate for another ICE username fragment. If the versions differ, a page with the check makes no offer or answer, so no channel opens and nothing about the file is sent. A page that finds another version closes its connection at once; a page that doesn't closes its own when the attempt ends. The sender sends no `refuse` at once, because the recipient's page handles a refusal at once while it may still be opening the signals that came before it, so a refusal could overtake the sender's marker that says which page is older. It sends `refuse` with `drop` for that attempt when 20 s have passed since the join (`SETUP_TIMEOUT_MS`), if it still hosts the link, as for a joiner that stays silent. The server ignores it when the joiner has left or a different attempt is bound, as the close of a recipient page that finds another version makes it, so it only unbinds a joiner that is still there, such as one that forged the marker, or a recipient page that finds no difference, which fails once refused (see "Retries and failures"). The sender's card then says which page needs a reload, and the recipient's page says so without "Try again" (see "Retries and failures"). A page from before the check drops the marker as a candidate for another ICE username fragment, since an ICE agent's fragment never contains `-`. A page loaded before 0019 hands it to the browser as an end of candidates, which Chromium 159 accepted on both sides in a manual run on 2026-11-26, still adding the candidates after it and, while every page ran version 3, opening the channel; Safari and Firefox weren't tested. Such a page can't say which page is older. Every page of a release sends the same marker, so the sealed message, which the server relays and logs as a `relay` line with its size, has the same size on every transfer of a release. The holder of the signal key, our server for an emailed link, can forge or change a marker, which only stops that attempt, as dropping its messages would, and holds the link for no longer than a silent joiner does.
- Both browsers start the connection with only the `stun:` URLs from `joined`, so no browser reserves a relay address while the direct routes are tried. This holds for pages loaded since `docs/decisions/0019-relay-only-as-fallback.md` went live, and so does every statement in this document that a pairing makes no relay allocation until the relay is added. A page loaded earlier, the sender's or the recipient's, starts with the full list and reserves relay addresses at once.
- Adding the relay is an ICE restart (0019). It happens only when `joined` lists `turn:` or `turns:` URLs: the sender allows the relay and a relay is up. When the sender has applied the recipient's answer, it waits 3 s (`RELAY_FALLBACK_MS` in `peer.ts`). If ICE hasn't connected by then and the sender's data channel hasn't opened, it adds the full ICE server list (`setConfiguration`), restarts ICE (`restartIce`) and sends `restart-offer`. The recipient adds its own full list and answers with `restart-answer`.
- ICE counts as connected when `iceConnectionState` is `connected` or `completed`. DTLS doesn't count, so a connection whose ICE is `disconnected` at 3 s also gets the relay added, unless its channel has opened. The sender doesn't add the relay once its channel has opened. The only ICE restart that starts after it read the path is one that recovers a dropped route, and that one never adds the relay (see "Recovering a dropped route").
- The recipient ignores a `restart-offer` that is in order but arrives while its ICE is connected or once its channel is open, before it checks the offer. It leaves its connection as it is and sends no `restart-answer`. That uses up its restart: it ignores every later `restart-offer` too, even once its ICE is no longer connected, until its open connection has reported a drop. The sender does the same with `restart-answer`: it ignores one that is in order but arrives while its ICE is connected or once its channel is open, before it checks the answer, and every later one too, until it gets a repeated `joined` with its channel open. So until a recovery starts, a page applies no restart SDP from the other side that arrives while its ICE is connected or once its channel is open, nor any later one, even one sealed by the holder of the signal key (our server, on an emailed link). "Recovering a dropped route" says what a page applies after that. A restart the sender started earlier doesn't complete on its side after it read the path, unless a recovery completes it.
- An honest `restart-offer` can cross the recipient's ICE connecting or its channel opening. The sender has then already added the relay and restarted ICE. It gets no `restart-answer`, and it doesn't take the relay back out before the attempt ends, so its browser can keep a relay allocation until then. The relay can then learn both IP addresses, although the recipient added nothing. In manual runs on 2026-11-25 with Chromium 159, the sender's browser made one allocation and asked the relay to let the recipient's address through, and the connection stayed on its first route.
- An honest `restart-answer` can cross the sender's ICE connecting or its channel opening. The recipient has then already added its relay and restarted ICE, and its browser can keep a relay allocation until the attempt ends. The sender's restart doesn't complete: it keeps its old remote description. Both browsers may then hold relay allocations. In a 60 s manual run on 2026-11-25 with Chromium 159, the connection stayed on its first route, the same pair of local addresses, with messages flowing both ways. That run's TURN URL couldn't be reached, so it compared only pairs of local addresses, not what a reachable relay would do. Safari and Firefox weren't tested for either crossing.
- Until a recovery starts, `restart-offer` and `restart-answer` are each accepted at most once per attempt: `restart-offer` only after the recipient answered the first `offer`, and `restart-answer` only after `restart-offer`. One that comes out of order, or after one that was accepted, is refused as a bad signal. In a recovery each can be accepted again, once per restart (see "Recovering a dropped route"). A second `offer` or `answer` is still refused, so the server can't replay a first one as a restart one. Both must name the same two DTLS certificates as the first `offer` and `answer`, the ones the safety number comes from: a page refuses the other side's restart SDP with another fingerprint as a bad signal, and closes with `setup-failed` if its own would name another. A page that ignores a restart SDP doesn't apply it either. So neither adding the relay nor a recovery can put anyone between the browsers after the number was fixed. A candidate whose `usernameFragment` is set and differs from the current remote description's is dropped silently, which drops candidates from before the ICE restart that arrive after it. If sending `restart-offer` or `restart-answer` fails, the peer closes with `signal-failed`. If `setLocalDescription` fails for either, it closes with `setup-failed`. If the sender's `setConfiguration` or `restartIce` throws, it doesn't add the relay, and the connection goes on without it. If the recipient's `setConfiguration` throws, it still answers, and the connection can still go through the sender's relay address. A recipient page loaded before 0019 treats `restart-offer` as a bad signal and ends the attempt. A sender page loaded before 0019 never sends `restart-offer`, so a recipient page loaded after it never adds the relay and can reach only the sender's relay address, which fails for a recipient that needs its own relay.
- The SDP carries the DTLS certificate fingerprints of the WebRTC connection. Because the server can't change them, it can't put itself between the browsers. For an emailed link it could, and with a safety number the two people see whether it did; without one they see nothing (see "The safety number").
- When the server stops on SIGTERM, as on a restart, it closes every socket with close code 4012, a private-use code (`main.ts`, decision 0025). If the WebSocket drops, the two pages behave differently. The sender's page opens a new socket after a growing, jittered delay, or at once after close code 4012, or 1012 from a server older than decision 0025 (`signaling-client.ts`), first takes back each transfer in progress whose attempt the server holds for it (see "Taking an attempt back on a new socket"), and then sends `host` again with all its links except emailed ones (`SendPage.tsx`): the server dropped their email binding with the old socket, so the page stops hosting them and their card says the emailed link stopped working (`server-lost` in `sender-state.ts`). A recipient whose data channel hasn't opened, on a socket that had opened, starts a new attempt at once with a new socket and a new attempt ID, up to 4 times (`MAX_REJOINS`), then fails (reaching the code step of an emailed link resets the count); a socket that never opened is left to the signaling client's own retries (`ReceivePage.tsx`). A restarted server only knows a link once its sender hosts it again, so a recipient refused with `starting` (the server's answer for a link it doesn't know yet, decision 0018) sends the same `join` again on the same socket after 1 s, and each `join` re-arms its 30 s connect timeout; `refused: unknown` always ends the attempt. A recipient on an emailed link sends `gate` first on every attempt; once the sender's socket has dropped or the server has restarted, no binding matches its value, so the page shows that the link no longer works (`unbound`). A recipient page that holds a resume token connects again and takes its attempt back instead (see "Taking an attempt back on a new socket"). Otherwise, once the data channel is open, the transfer no longer needs the server while the route between the browsers holds, so a drop of the recipient's socket only closes signaling: the page opens no new socket. Such a page can no longer ask for a recovery (see "Recovering a dropped route").
- Accepted residue: the sender learns the attempt ID from the server's `joined`, so a lying server could replay one old attempt's recipient signals to the sender. That only breaks that attempt: the replayed answer names a DTLS fingerprint of a closed connection, so no channel opens.

### Recovering a dropped route

`apps/web/src/lib/peer.ts`, `apps/web/src/receive/ReceivePage.tsx`, `apps/web/src/lib/sender-state.ts`, `apps/web/src/send/SendPage.tsx`, `apps/server/src/signaling.ts`, `docs/decisions/0031-ice-restart-recovery.md`

When the route between the two browsers drops after the data channel opened, the pages try to get a route back by an ICE restart on the same connection (0031). The data channel, both certificates, the file key and the safety number stay the same, frames go on from the next sequence number, and the pages show no new text: progress stops and then goes on. It is the same for a file and a shared secret, at any point after the channel opened.

```
recipient              its connection reports "disconnected"
recipient → server     join {link, attempt}                 the same message again, token included
server    → both       joined {link, attempt, iceServers, turn}   ICE servers made now
sender    → recipient  relay seal_s({restart-offer, sdp})  after restartIce()
recipient → sender     relay seal_r({restart-answer, sdp})
both                   relay seal({ice, candidate})        trickle
```

- **Scope.** A recovery needs both pages' signaling sockets. It covers a route that drops while both sockets stay open, such as a short loss of Wi-Fi or a route that flaps on the same address. A page that loses its socket too, as a real change of network makes it, first takes its place back on a new socket, when its attempt is armed and the page comes back within the hold (see "Taking an attempt back on a new socket"). Then the recovery goes on as below. Otherwise it is not recovered: a recipient whose socket dropped after the channel opened has closed its signaling client and can't ask, and a sender whose socket dropped has lost its binding on the server, so the recipient got `host-gone` and doesn't ask. Such a transfer ends as before 0031, when a browser reports `failed`, and the recipient's "Try again" continues a file (see "Continuing after a drop").
- **The recipient asks.** After its channel has opened, each time its `connectionState` becomes `disconnected`, the recipient's page sends the same `join` again on the same socket, at once, or, while it waits to take its attempt back on a new socket, once the server gave it back: the same link, the same attempt ID and, on an emailed link, the same token, with no `gate` first. It asks once per such change and never on a timer. On `failed` it asks only while a recovery deadline runs (below); a `failed` with no repeated `joined` in that drop closes the connection at once and sends nothing. It doesn't ask before its channel has opened, once the attempt has ended or the transfer has stopped, or after `host-gone` in that attempt, when the same `join` would be a new pairing with the sender's new socket. The sender's page never asks.
- **The server answers a repeated join like a first one.** It checks the token again on an email-bound link, counts the join toward the link's 10 pairings per 30-second window, logs `joined`, and sends `joined` to the recipient and then to the sender. The ICE servers and `turn` are made at that moment: new TURN credentials when the sender allows the relay then and a relay is up then, else only `stun:` URLs. Past the 10 pairings it logs and answers `refused` with `busy`; without a token the link's binding issued it logs `refused` with `unverified` and answers `gate` with `to: ""`. Either way the recipient stays bound and can ask again on the same socket.
- **The answers the recipient's page ignores.** Once its channel is open, the page lets none of these end the transfer: `refused` with `busy` (the server's cap, or a sender's page from before 0031, which refuses a repeated `joined`), any `refused` after `host-gone` (the server's answer to a `join` that crossed it), `gate`, and `error` (a server from before 0031 answers `already-joined`). `refused` with `drop` or `used` still ends the attempt. A `joined` with this attempt's ID goes to the connection, which ignores it unless it has reported a drop in this attempt.
- **The sender restarts ICE.** A `joined` that carries the attempt ID of the link's attempt in progress is not refused with `busy`. The sender's page hands its ICE servers to that attempt's connection, which sets them (`setConfiguration`), calls `restartIce()` and sends a new offer as `restart-offer`. While that offer waits for its answer, a later repeated `joined` only sets its ICE servers and makes no second offer; only the next `restart-answer` ends the wait, not the connection being `connected` again. Until its own channel has opened, the connection ignores a repeated `joined`. A `joined` with any other attempt ID is refused with `busy` as before, and after delivery with `used`. If the sender's page has already given up the attempt, the repeated `join` can cross its refusal, and the server, having unbound the recipient, pairs it as a first join. The sender's page keeps, in page memory only, the attempt ID of the recipient's last attempt that ended, and refuses a `joined` that carries it with `drop` (`used` after delivery). It starts no connection, so that `joined` doesn't count against a safety-number link's 5 tries; the server logs it as one more `joined` line and a `refused` line with `drop`.
- **Restart signals in a recovery.** From the first time its open connection reported a drop, the recipient applies every `restart-offer` that is in order and answers with `restart-answer`, whatever its ICE state and with its channel open. It does so also when its page didn't send the `join`, for example after `host-gone`. From its first repeated `joined` with its channel open, the sender applies a `restart-answer` only while an offer of its own waits for an answer (`signalingState` is `have-local-offer`) and ignores any other. Before that, the rules for adding the relay hold. Every restart SDP must still name the two certificates of the first `offer` and `answer`, or the page refuses it as a bad signal, and a second `offer`, `answer` or `commit` is still refused. A `restart-offer` or `restart-answer` that can't be sent in a recovery doesn't close the connection; the deadline ends it if no route comes back.
- **The relay.** A recovery never adds the relay. A page gives its connection the new list's `turn:` and `turns:` URLs only if this connection had already added the relay; otherwise it sets only the list's `stun:` URLs. So a pairing that connected directly reserves no relay address when its route drops either, and a direct route that doesn't come back is not replaced by the relay. A connection that had added the relay gets the new list as it is: with new credentials when the sender allows the relay and a relay is up at that `joined`, and with no TURN URL otherwise, so the restart then gathers no relay address. A sender that refuses the relay passes only `stun:` URLs, as at the first `joined` (see "Refusing the relay").
- **The deadline.** A repeated `joined` that a page acts on starts a deadline of 30 s (`RECOVERY_TIMEOUT_MS` in `peer.ts`) on that page, unless one already runs. The connection becoming `connected` ends it. When it runs out and the connection is not `connected`, the page closes with `connection-failed`: the sender refuses the recipient with `drop`, and the recipient's page keeps what arrived of a file for "Try again", as for any dropped connection. While a deadline runs, the browser's `failed` doesn't close the connection. With no repeated `joined`, as when the server answered `busy` or the other page's socket is gone, `failed` closes it at once, so a page whose other side is gone waits no longer than before 0031. A deadline that started on a page whose connection was still `connected` starts again with its full 30 s if that connection leaves `connected` while it runs, and runs its 30 s and then does nothing if it never does.
- **The path.** Each time its connection becomes `connected` again after the channel opened, a page reads the path again and shows it, and the sender's page runs the relay backstop on it (see "Refusing the relay"). A page whose connection never left `connected` during the recovery, as the sender's stayed in two of six measured runs, reads nothing again. The sender reports the path to the server once per connection, so the server's `path` line still says how the connection first opened.
- **What the server learns.** Before 0031 the server saw nothing of a pairing after the sender's `path` report, until a socket closed or the sender sent `refuse`. Now the repeated `join` tells it that this pairing's route dropped, and when the recipient's browser noticed. It logs that as a second `joined` line for the link's first 6 characters, or a `refused` line with `busy` past the cap, or `unverified` when its token doesn't fit, or, when the `join` crossed the sender's refusal, a `joined` line and a second `refused` line with `drop`, and as `relay` lines for the `restart-offer`, the `restart-answer` and the new candidates (see "Where traces are kept"). It learns neither why the route dropped nor on whose side, nor how far the transfer had got, nor whether the recovery worked: a recovery that fails shows only as the `refused` with `drop` that ends any dropped attempt, and one that works shows as nothing more. A drop the browsers get through before the recipient's browser reports `disconnected` leaves no trace.
- **What the server can do with it.** On any link it can send a `joined` nobody asked for. The sender then restarts ICE. A recipient whose connection has reported no drop ignores both the `joined` and the `restart-offer`, so the sender gets no answer and stays on its route; one that has reported a drop answers, and the restart completes. Once the pages apply more than one restart signal, it can also replay a sealed `restart-offer` or `restart-answer` of this attempt. The worst either does is end the transfer, which the server can already do by dropping messages or replaying a first `offer`. It can't read or change the file: every restart SDP must name the two first certificates. On an emailed link the holder of the signal key, our server, can seal a `restart-offer` of its own once the recipient's connection has reported a drop, and so move the encrypted stream onto a route through an address it picks, mid-transfer. It could already pick the route at setup. It then sees what a relay sees: both IP addresses, sizes and times, and ciphertext under DTLS keys it doesn't have. The certificates stay pinned, so a safety number still covers the connection.
- **What was measured.** `apps/e2e/tests/networks.spec.ts` ("a route cut mid-transfer", in `pnpm e2e:networks`) cuts UDP between the two sites mid-transfer, on a direct path with the relay refused, and restores it once the recipient has asked. In six timed runs on 2026-11-27 with the suite's Chromium, the route was cut for about 6 to 8 s. The recipient's browser reported `disconnected` 5.3 to 7.5 s after the cut, its `join` went out within 10 ms, and `joined` came back 140 to 190 ms later, once about 600 ms. The offer and answer of the restart completed on both pages while the route was still cut, and the recipient was `connected` again 300 to 400 ms after the route came back. The file arrived with a matching SHA-256 on one `RTCPeerConnection` per page, with a new ICE password on both, and no frame was lost. With the sender's restart turned off, the route also came back by itself in that test, so Chromium gets through a cut that short without the restart too.
- **Not measured.** When a browser reports `failed`; a repeated `join` on `failed`; an outage longer than about 8 s; the 30 s deadline in a browser (a unit test with mock timers covers it, `apps/web/src/lib/peer.test.ts`); a second repeated `joined` before the first restart's answer; a recovery on a relayed connection, and whether a restart then makes new relay allocations; which route carries the data after a recovery; Firefox and WebKit. Nothing here was run in a second browser engine.
- **Older pages and servers.** A recipient page from before 0031 never asks. A sender page from before it refuses the repeated `joined` with `busy`: the server unbinds the recipient, whose page ignores the refusal, and with no restart the transfer ends when a browser reports `failed`, or when the recipient's deadline runs out, unless the route came back by itself. A server from before it answers `already-joined`, which the recipient's page ignores.

### Taking an attempt back on a new socket

`apps/server/src/signaling.ts`, `apps/web/src/lib/receive-guards.ts`, `apps/web/src/receive/ReceivePage.tsx`, `apps/web/src/lib/sender-state.ts`, `apps/web/src/send/SendPage.tsx`, `docs/decisions/0033-signal-socket-takeover.md`

A real change of network, such as a laptop moving from Wi-Fi to a phone's hotspot, changes the page's IP address. That drops the route between the browsers and the page's signaling socket too. Once a transfer's connection has opened, the page connects again and takes its place back in the same attempt with a resume token (0033). The route is then recovered as above, on the same connection, with the same attempt ID, certificates and safety number, and the pages show no new text.

```
sender    → server     path {link, path}                    once its channel opened
server    → sender     resume {link, attempt, token}        the sender's token
server    → recipient  resume {link, attempt, token}        the recipient's token
                       a page's socket drops, and the page connects again
page      → server     resume {link, attempt, token}        first on the new socket
server    → page       resume {link, attempt, token}        a new token; with none, refused
server    → both       joined {link, attempt, iceServers, turn}   only as below, then the restart above
```

- **Arming.** When the sender reports a `path` other than `failed` and the link's recipient is still bound, the server arms that attempt: it makes two resume tokens, one per side, and sends each page its own in `resume`. A token is 16 random bytes in base64url. It derives from nothing: not from the link secret, a key or the attempt ID. The server compares it in constant time. It lives only in the server's memory and in its own page's memory, is never logged and never goes in storage or a URL. An attempt that isn't armed, such as one whose socket drops during setup, ends as before 0033.
- **The hold.** When a socket closes with no close frame (1006), as when its network goes, the server keeps that side's place in each armed attempt the socket held for up to 30 s (`TAKEOVER_MS`), and no longer than the heartbeat at which the socket would have been ended had it stayed open. So a held side is forgotten within a minute of its page's last sign of life. Every other close frees the attempt at once, as before: a close frame (1000 when a page navigates away, 1001 when Chromium closes the tab or Caddy reloads, decision 0025), the server's policy close, an `error` from `ws`, the heartbeat, the end of a socket that stopped reading, and a server stop. While a side is held, the other page hears nothing of it: no `host-gone` or `left` goes out, a `host` for the link from another socket gets `error` with `already-hosted`, another socket's `join` gets `refused` with `busy`, the bound recipient's repeated `join` gets `refused` with `busy` and stays bound, and a `relay` to the held side is dropped and logged as `relay-dropped`. The hold ends early when the attempt ends on the other side: that side's socket closes in a way that isn't held, or the sender refuses the attempt or stops hosting the link. When a hold ends without a takeover, the server does what that close did before 0033, with the same messages and log lines, up to 30 s later. When the sender's side ends while the recipient's is held, the log shows `left` and no `host-gone`.
- **The takeover.** The page's new socket sends `resume` with the link, the attempt ID and that side's current token. The recipient's side takes a socket bound to no link that hosts nothing, and the sender's side a socket that is no recipient. The server moves that side's place to the new socket: on the sender's side the link and an emailed link's binding, while the attempt keeps the old socket's relay choice until the new socket sends `host`. It answers `resume` with a new token, which replaces the used one, and logs `resumed`. If the old socket is still open on the server, as a socket on a lost network can be until the heartbeat ends it, the server ends it with `terminate()`. Its idle links are then unhosted at once and its other armed attempts held, as at a lost network.
- **Refusals.** The server answers `resume` with no token, logs `resume-refused` and changes nothing when the token is wrong, used, the other side's or another link's or attempt's, when the attempt was never armed, has ended or its hold ran out, when the socket has the wrong role, and when the socket already holds that side. Every refusal looks the same.
- **The restart.** The server notes each repeated `join` from the bound recipient in an armed attempt, held sender or not, and clears the note when the sender next relays something to the recipient: a repeated `join` can reach the server while the sender's old socket only looks open, so its `joined` reaches nobody. After a takeover of the sender's side with the note set and the recipient's socket open, the server sends `joined` to both, which logs `joined` and counts toward the link's 10 pairings, and the sender restarts ICE. Past the cap it logs and sends `refused` with `busy` instead, and only the recipient's next repeated `join` can get a restart. After a takeover of the recipient's side the server sends nothing more: a recipient whose connection reported `disconnected` while it had no socket sends its repeated `join` once the takeover succeeded.
- **The recipient's page.** While it holds a token it hasn't sent, a dropped socket doesn't end the attempt or close signaling, even before its own channel opened (`onSocketClose`, `onSocketOpen` and `resumeAction` in `receive-guards.ts`). The client opens a new socket, which sends `resume` instead of `gate` or `join`. A stall of its connection meanwhile sends nothing until the answer. A page sends each token at most once. A `resume` without a token, or a new socket that closes before the answer, makes the page go on as before 0033: once its channel is open, it closes signaling.
- **The sender's page.** It keeps each link's token, with its attempt, in memory until a new connection for that link starts. On a new socket it sends `resume` for each recipient still in that attempt, and sends `host` only once the server answered every one. A link whose `resume` is refused, or whose socket closed before the answer, is then treated as after any lost socket: an emailed link's card says it stopped working (`resume-refused` in `sender-state.ts`). A recipient whose attempt came back stays as it was, an emailed one bound. When an open connection reports `disconnected`, the page sends its `host` again, unchanged, so a socket that died without closing surfaces: a write on it should draw a reset that closes it, as a write from the recipient's page did behind the suite's stand-in for the load balancer (the sender's own case and AWS's load balancer are not tested). On a live socket an unchanged `host` changes nothing and logs nothing, except the `error` line with `already-hosted` again while another socket still holds one of its links.
- **Pages that leave.** Both pages close their signaling client with 1000 on `pagehide`, unless the page may come back from the back-forward cache, so the server frees their attempts at once.
- **What the server learns.** That a page's socket dropped during a transfer and came back, and when. From the two sockets' addresses, it learns that the new address continues the old one. Addresses are still never logged. The `resumed` and `resume-refused` lines carry only the link's first 6 characters, never the token, the attempt ID or the side. A token lets its holder take one side of one attempt and cut off the page that had it, which our server can already do. It opens no sealed signal and no file, because it holds no key.
- **Not covered.** A socket that drops before the sender reported its path; an outage longer than the hold; a socket that a proxy closes with 1001; a server restart, which forgets every token, so each page's `resume` is refused. Those transfers end as under "Recovering a dropped route". The sender's idle links behind a silent socket still wait for the heartbeat. A takeover needs the new socket to reach the server process that holds the attempt: signaling runs as one process.
- **What was tested.** `apps/e2e/tests/takeover.spec.ts`, in `pnpm e2e`, cuts the recipient's or the sender's socket mid-transfer inside the browser: the page's side closes, while the server's side stays open and hears nothing more. It also makes both connections report a dropped route. The file arrives with a matching SHA-256 and no "Try again", on one connection and one attempt ID per page, with a new ICE password, and the server ends the old socket within 5 s. So the browser test covers the takeover of a socket that is still open; the hold after a 1006 close is covered by unit tests in `apps/server/src/signaling.test.ts`. `apps/e2e/tests/networks.spec.ts`, in `pnpm e2e:networks`, also makes the change real: site B's router takes a new public address mid-transfer and forgets its NAT mappings, so the recipient's socket and its route die at once. The next segment of the old socket, now from the new address, draws a reset from the nginx stand-in for the load balancer, the page takes its attempt back on a new socket, and the ICE restart finds the new address. The file arrives with a matching SHA-256 and no "Try again", on one connection and one attempt ID per page, with a new ICE password, one `resume` sent and a `resumed` line in the signaling log. This test does not check when the server ends the old socket. Whether AWS's load balancer answers with a reset too is not tested.
- **Older pages and servers.** A page from before 0033 ignores `resume` and ends as before. A page on a server from before it gets no token and never sends `resume`. A page that got a token and then meets an older server after a rollback sends `resume`, which that server answers by closing the socket with 1008; the page counts that as refused and goes on as before.

## The safety number

`apps/web/src/lib/check.ts`, `apps/web/src/lib/peer.ts`, `apps/web/src/lib/send-file.ts`, `apps/web/src/lib/sender-state.ts`, `apps/web/src/receive/ReceivePage.tsx`, `docs/decisions/0017-check-number.md`, `docs/decisions/0024-safety-number-buttons.md`

The sender chooses per recipient, when adding them, between two buttons: "Add" and "Add with safety number" ("Add and email link with safety number" and "Add and email link" once they choose email). The first button, which Enter presses, is the plain link for a link the sender passes on themselves and the safety number for a recipient Fidant emails. In Swedish the number is called "kontrollnummer". With it on, both pages show a six-digit number from that exact connection before anything about the file goes. The recipient reads theirs aloud and the sender compares it with their own screen.

- **Every connection, check on or off,** makes a fresh ECDSA P-256 DTLS certificate on each side (`RTCPeerConnection.generateCertificate`). Right after its version marker (see "Connecting the two browsers"), the recipient sends a commit, `base64url(SHA-256("fidant-commit-v1\n" ‖ its fingerprint))`. The sender makes its offer only after the commit arrives, refuses a second commit, and refuses an answer whose fingerprint does not hash to the commit (`bad-signal`). The recipient in turn refuses to answer unless its answer names the certificate it committed to (`setup-failed`). Every fingerprint line of an SDP, in any spelling, must be the exact `a=fingerprint:sha-256 <value>` form, and all of them must name one certificate, or the page refuses the SDP before the browser sees it. After the browser parses the other side's description, the page reads the fingerprint back from the browser's own copy and refuses any difference, because browsers disagree about which odd spellings they still read. A fingerprint is the upper-case colon hex the SDP carries.
- **The number** is the first 8 bytes of `SHA-256("fidant-check-v1\n" ‖ offer fingerprint ‖ "\n" ‖ answer fingerprint)`, read as an unsigned big-endian integer, modulo 1,000,000, with leading zeros, shown as two groups: `482 913`. Each page reads both fingerprints from its own offer and answer, the ones its browser checks the DTLS handshake against. The number is shown on screen and never sent, logged or stored.
- **Someone in the middle,** our server included for an emailed link, holds two connections, one to each browser, so the two pages show numbers from different fingerprints. Because the recipient commits first, it has to fix both of its certificates before it learns the sender's, so each new connection is one blind guess at a match: one in a million.
- **The offer says whether the check is on** (`check`). For an emailed link our server can read and flip it. Then one page shows a number and the other doesn't, and the file still waits: the page that expects CHECK gets META, or the other way round, and stops.
- **Confirming.** With the check on, both pages hold the file until both people confirmed, with CHECK frames (see "Frames"). "It matches" in the sender's dialog, which names the recipient, and "They said it matches" on the recipient's page each send CHECK 1. "It differs" or "They said it differs" sends CHECK 0 and ends the attempt on both pages. The link still works after a mismatch, because a misheard digit is the likely cause. "Not now" or Escape only closes the sender's dialog: the 5-minute limit keeps running, and the recipient's card offers "Compare number" to open it again. The dialog shows one recipient at a time, and its two answer buttons stay disabled for half a second after it shows a recipient, so a click already on its way to the previous check cannot answer this one.
- **The sender's own click protects the file.** Someone in the middle is one end of the sender's encrypted channel, so it can send the sender a CHECK 1 of its own. The sender's card never shows the recipient's answer as a sign the check passed. The recipient's click protects the recipient only when the offer arrives with the check on: it holds back a file sent by someone in the middle. Someone in the middle writes the offer and can set the check off, and then the recipient's page shows no number and asks for no click.
- **How many guesses.** Our server learns the sender's number as soon as it has the offer, and the recipient's from the answer, before either channel opens. So both sides limit new connections:
  - The sender's page counts, per link with the check on, every attempt that ended before both confirmed: a drop, a timeout, the recipient leaving, a server drop, a refused relay, a mismatch, or a check not confirmed within 5 minutes (`CHECK_TIMEOUT_MS`). A shared secret refused because its connection is too small doesn't count: with the check on, the sender's page refuses it only after both confirmed. An attempt that the sender's page ends because it finds another version doesn't count: it ends before the offer, so it gives nobody the sender's number. When only the recipient's page finds another version, as with a sender's page from before the version check, the sender's page counts the attempt. At 5 (`CHECK_ATTEMPTS`) it stops hosting the link; the card says the check failed 5 times and to add the recipient again for a new link, and the recipient's page then says the link isn't active. The count stays in the page and is never sent.
  - Once the recipient's page has sent its answer, it never makes a new connection by itself: a socket that drops before the channel opens ends the attempt, and only "Try again" or a reload makes a new connection. Recovering a dropped route is no new connection: it keeps both certificates, so the number stays the same and nobody gets a new guess (see "Recovering a dropped route"). A `token` counts only as the answer to a code the page sent.
  - So every guess after the first in an attempt costs the recipient a visible failed connection and a click. Ten connections in all give at most 1 in 100,000.
- **What it doesn't prove.** Our server also serves the page, and a page that skips the check can't be caught by it. The check shows that nobody sat in the middle of this connection, not that the page code is honest (see "What Fidant doesn't protect against"). It also does nothing for a link created without a safety number, or for a sender who clicks "It matches" without comparing.
- **Pages from before the safety number** can't connect to pages after it: the old sender refuses the commit, and the new sender waits for a commit an old recipient never sends. Reload both.

## Two layers of encryption

WebRTC encrypts the data channel with DTLS. Fidant doesn't rely on that: every frame on the channel after INIT is also encrypted with AES-256-GCM under the file key, which only the two browsers hold. For an emailed link our server had the link's secret, so by sitting in the middle it could derive the file key too; with the safety number on, it would get no further than INIT and CHECK. INIT is sent in clear and carries only the random transfer ID, which with the recipient's attempt ID is the file key's salt; changing it changes the key, so the next frame fails to decrypt, and replaying it into another attempt gives the recipient a different key.

## Frames

`apps/web/src/lib/frames.ts`

```
frame  = header(10) ‖ body
header = version(1) = 4 ‖ kind(1) ‖ seq(8, u64 big-endian)   plaintext, and the AES-GCM additional data
body   = AES-GCM(file key, iv, aad = header), 16-byte tag
iv     = direction(1: 0 sender, 1 recipient) ‖ 00 00 00 ‖ seq(8)
```

| Kind | Name    | From      | Body                                                                                                         |
| ---- | ------- | --------- | ------------------------------------------------------------------------------------------------------------ |
| 0    | INIT    | sender    | transfer ID (16), in clear, the only unencrypted frame                                                       |
| 1    | META    | sender    | exactly 1,024 bytes: length(2) ‖ JSON `{name, size, type, chunkSize, from}` ‖ zeros                          |
| 2    | CHUNK   | sender    | exactly `chunkSize` bytes of file, zero-padded after the end of the file                                     |
| 3    | END     | sender    | SHA-256(32) ‖ size(8), of the whole file                                                                     |
| 4    | CHECK   | sender    | 1 byte: 1 the safety number matches, 0 it differs                                                            |
| 16   | ACCEPT  | recipient | offset(8, u64): the CHUNK bytes the recipient already holds, a multiple of `chunkSize`, 0 for a new transfer |
| 17   | RECEIPT | recipient | SHA-256(32) the recipient computed                                                                           |
| 18   | DECLINE | recipient | empty                                                                                                        |
| 19   | CREDIT  | recipient | granted(8, u64): how many CHUNKs in all the sender may send in this attempt                                  |
| 20   | CHECK   | recipient | 1 byte: 1 the safety number matches, 0 it differs                                                            |

- Sequence numbers start at 0 in each direction. A reader accepts only the next one, and stops for good after any failure, so a dropped, reordered, repeated or altered frame ends the transfer.
- The two directions use different nonces because the direction is in the IV.
- Changing INIT changes the derived key, so META then fails to decrypt. Replaying a recorded INIT and META into a later attempt fails the same way, because that attempt's new attempt ID gives the recipient a different key, and the recipient sends nothing back.
- Each kind has a fixed direction and body size range; anything else is rejected.
- Version 2 added CREDIT, version 3 added the attempt ID to the file key's salt, and version 4 gave ACCEPT its offset. The version marker carries the frame version too (see "Connecting the two browsers"), so it goes up for any change that breaks frames or signal payloads. The marker is itself sealed, so a change to the signal key, its HKDF info or additional data, or the seal layout makes it unreadable: the check can't catch that, and the page fails with `bad-signal`, shown as a lost or dropped connection. A browser rejects a frame of any other version as an unknown version, INIT included, so both pages must run the same version. Pages with the version check compare versions before they connect. A page that sends no marker counts as version 3, so a page with the check stops before the offer and no frame passes between them. A frame of another version can still arrive when a page's marker doesn't match its frames, for example a marker forged by the holder of the signal key: it fails at INIT on the recipient's side, before any key is derived, and the sender sees only the connection close. A recipient's page with the check then says which page needs a reload, as for a version marker. A recipient's page from before the check shows the same message as for unreadable data.

## The transfer

`apps/web/src/lib/send-file.ts`, `apps/web/src/lib/receive-file.ts`

1. When the file is chosen, or each time a shared secret changes, the sender's browser computes its SHA-256 (`apps/web/src/lib/sha256.ts`, streamed in 4 MiB slices).
2. INIT, then, with the safety number on, CHECK from each side once its person compared the numbers (see "The safety number"), then META. The recipient sees the name, size, type and the sender's typed name (for a shared secret, only the sender's name), and chooses.
3. The recipient sends ACCEPT or DECLINE, encrypted. ACCEPT carries the offset to start from: 0, or the CHUNK bytes a dropped attempt kept (see "Continuing after a drop"). It also proves that the recipient holds the key. No file data is sent before it. After DECLINE the link still works.
4. CHUNK frames from the offset on, `chunkSize = min(48 KiB, maxMessageSize − 64)` (64 is `FRAME_OVERHEAD_BYTES` in `frames.ts`: the 26-byte header and tag, with margin), sent while the channel buffer holds at most 4 MiB (`bufferedAmount`) and only within the recipient's credit: right after ACCEPT the recipient sends CREDIT for 128 chunks (`CREDIT_WINDOW_CHUNKS` in `receive-file.ts`), and every 64 chunks its sink writes it raises the credit to 128 past what is written. The sender sends this attempt's CHUNK i (counting from 0 at the offset) only while i is below the highest CREDIT. END needs no credit.
5. END with the checksum and the exact size of the whole file, also when the attempt started at an offset.
6. The recipient checks and sends RECEIPT with the checksum it computed. The sender marks the link delivered only when it matches. RECEIPT is the recipient page's word, not proof that the file arrived: END already carries the checksum, so a modified recipient page, which holds the key anyway, can send an offset equal to the padded length, get END alone and send its checksum back. The sender's card then shows the link delivered with no CHUNK sent.

### Checking on the recipient's side

`ReceiveVerifier` in `frames.ts` hashes the file bytes as they arrive and checks that every CHUNK is exactly `chunkSize`, the padding is zeros, the chunks add up to the padded length, and END's size and checksum match what arrived. Only then is the file finished. A lost connection can leave what arrived for the next attempt (see "Continuing after a drop"). Other endings, such as a frame that fails to decrypt, the wrong order, too much data or a checksum that doesn't match, abort the sink, which discards what was written.

META's `chunkSize` must be at least 986 bytes (`MIN_CHUNK_BYTES`): the META frame (1,050 bytes) must fit the channel, so no honest sender's chunk is smaller, and a sender that claims tiny chunks can't make an in-memory recipient hold millions of separate parts. A recipient holds at most 129 incoming frames that it hasn't handled yet (the window and END), and a sender at most 8. One more ends the transfer as a broken format (`createInbox` in `inbox.ts`), so a sender that ignores its credit can't fill the recipient's memory: what waits for a slow sink stays at about 128 × `chunkSize`, 6 MiB at 48 KiB, whatever the file's size.

`apps/web/src/lib/sink.ts`: where the browser has `showSaveFilePicker` (desktop Chromium browsers), the file streams to a place the recipient chose. Elsewhere it is collected in memory as a Blob and downloaded at the end, and an offer of a file over 256 MiB warns the recipient of that (`BLOB_WARN_BYTES`). A shared secret is always collected in memory and never downloaded (see "Sharing a secret"). The Blob is always `application/octet-stream`, whatever type the sender claims, so a file can't run as a page in Fidant's origin. Between attempts, a kept part stays in the Blob's parts in page memory, or in the file from the save dialog, which the page leaves open: it neither closes nor aborts it. Whether a browser keeps that file writable over a new connection and minutes of waiting, and what it does with the unfinished file when the tab closes, is not tested yet (planned in FID-322).

### Continuing after a drop

`apps/web/src/lib/receive-file.ts`, `apps/web/src/receive/ReceivePage.tsx`, `apps/web/src/lib/receive-problem.ts`

If the route drops while a file arrives, the pages first try to recover it on the same connection, which needs no click and loses nothing (see "Recovering a dropped route"). When that fails, or can't be tried because a page has lost its signaling socket, the connection ends as dropped. The recipient's page can then keep what arrived and continue from there on "Try again", in the same page load.

- It keeps the CHUNK data that arrived, in the sink, with `ReceiveVerifier`'s running SHA-256 and position. Only bytes from frames that decrypted in order and passed the checks on each CHUNK are written to a sink.
- `receiveFile` hands the part back only when the attempt ended as a lost connection, no check had failed, END hadn't arrived, the last write had finished, the offer wasn't a shared secret and the recipient hadn't said the safety numbers differ. It waits for a write still pending when the connection drops, and keeps nothing if that write fails. The page keeps the part only when the attempt ends on a failure that offers "Try again", such as a dropped connection, the sender's `refuse` with `drop` or a connection that never opened. Other endings discard it, such as a decline, a safety number that differs (which still offers "Try again"), a frame that fails a check, a checksum mismatch, a failed write or another version. The recipient saying the numbers differ discards it at once, even after the connection dropped.
- "Try again" makes a new attempt like any other: a new socket and attempt ID, a new transfer ID and file key, and frames numbered from 0. With the safety number on, the two people compare the new number first, and nothing is written before both confirmed. When META arrives, the page compares it with the kept one. If every field is the same (`name`, `size`, `type`, `chunkSize`, `from`), it shows no offer and no save dialog: it sends ACCEPT with the offset, the CHUNK bytes it holds, and shows the download going on from there. If any field differs, it discards the part, shows the offer and answers with ACCEPT 0 or DECLINE.
- The sender refuses an offset that is not a multiple of `chunkSize` or lies past the padded length: it sends no CHUNK and ends the attempt as a dropped connection, and the link stays usable. Otherwise it sends the CHUNKs from the offset on, then END with the whole file's checksum, and its card counts progress from the offset. An offset equal to the padded length gets END alone (see step 6 of "The transfer").
- The verifier goes on from the kept checksum and position, so END's size and checksum cover the kept bytes and the new ones together. A sender that sends different bytes after the offset ends in a checksum mismatch: the page discards the file and sends RECEIPT with the checksum it computed, and the sender's card fails.
- A shared secret always starts over: `receiveFile` never hands one back.
- A new attempt refused with `busy` while a part is kept, for example because the sender's page still holds the last connection, ends on a failure that says so, with "Try again", and the part stays.
- The page discards the part when it shows anything other than a failure with "Try again", for example a link refused as `used` or `unknown`, a sender's page that closed, or another version. A close or reload ends it too: a part in page memory is gone, and the page can no longer continue a part in the save dialog's file, whose unfinished file is then left to the browser (see "Checking on the recipient's side").
- Limits: "Try again" while the sender's page is reconnecting to our server and hosting its links again can be refused as `unknown` or told the sender is gone (see "Retries and failures"), which discards the part. A "Try again" clicked before the page has finished winding down the last attempt can start from zero. Nothing continues after a reload.

### Names

META refuses names, types and sender names containing C0 or C1 control characters, line and paragraph separators (U+2028, U+2029), any Unicode Bidi_Control character (U+061C, U+200E, U+200F, U+202A–202E, U+2066–2069), a filler that always draws as blank (U+115F, U+1160, U+2800, U+3164, U+FFA0, U+13441, U+13442, U+16FE4, U+1D159) or three or more spaces of any kind (also when invisible characters such as U+200B sit between them), so a name ending in `.exe` can't be displayed as one ending in `.pdf` or have its ending pushed out of sight. A single space of any kind is allowed, since macOS puts U+202F in screenshot names (`hasForbiddenCharacters` in `packages/protocol`). The sender's name is typed by the sender and not verified.

## Padding

`paddedLength` in `frames.ts`

Anyone who sees the encrypted traffic (the networks, our relay) sees frame sizes. So:

- The size is rounded up with Padmé (Nikitin et al., 2019), which adds at most 12 %, then up to a whole number of chunks. An empty file is padded like a 1-byte file.
- Every CHUNK frame has the same length. The exact size travels only inside the encrypted META and END.
- META is always 1,024 bytes, so the name's length doesn't show.
- CREDIT is a small encrypted frame of fixed size. Its timing shows only how fast the recipient writes, like the timing of any other frame.
- A download that continues after a drop (see "Continuing after a drop") keeps every frame at its usual size: ACCEPT is always 8 bytes, whatever its offset. The new attempt shows only the rest of the file. Someone who sees both attempts, such as the networks, or the relay when both went through it, can add them up to at least the padded size one whole transfer shows, more by any chunks sent in both attempts, and learns no more about the file's size than from that.
- A shared secret is at most 32 KiB. When `chunkSize` is at least 32 KiB (a maximum message size of at least 32,832 bytes), every shared secret pads to exactly one CHUNK. The code enforces this (`textFitsOneChunk` in `text-secret.ts`): in secret mode, a connection that allows less never gets META or the secret, and that recipient's card says the secret wasn't sent. With the check off, it gets nothing, not even INIT (checked in `SendPage.tsx` when the data channel opens). With the check on, the sender's page sends INIT and runs the check as for a file, so whoever holds the link can't tell a shared secret from a file before both confirmed; once both have, it refuses the recipient before META (`minChunkBytes` in `send-file.ts`). The check uses the 32 KiB limit, never the shared secret's own size, so a refusal says nothing about the length. So all shared secrets on a connection have the same frame sizes. When the maximum message size is at least 49,216 bytes, `chunkSize` is 48 KiB, and a shared secret then has the same frame sizes as any file of up to 48 KiB.
- Measured on 2026-11-24 with Playwright's browser builds: Chromium 159 and WebKit 27.2 report a maximum message size of 262,144 bytes, Firefox 159 reports 1,073,741,823, and pairs of different browsers settle at 262,144. When a browser reports none, the app uses 65,536 (`DEFAULT_MAX_MESSAGE_SIZE` in `peer.ts`). So today every shared secret crosses the network as one 48 KiB CHUNK.

An observer learns a file's size only roughly, plus the chunk size, which follows from the connection's maximum message size. A shared secret's length doesn't show at all: a shared secret is sent only over a connection whose maximum message size is at least 32,832 bytes, which every browser measured above allows.

## Sharing a secret

`apps/web/src/lib/text-secret.ts`, `apps/web/src/send/SendPage.tsx`, `apps/web/src/receive/ReceivePage.tsx`

The send page in secret mode (`/send/secret`) sends a secret the sender types or pastes instead of a file, over the transfer above unchanged: the same keys, frames, checks, RECEIPT and one-time links. A shared secret is never kept after a drop, though: every attempt starts over. The server, the relay and the signaling messages are the same as for a file, and so is emailing the link (see "Emailed links").

- The sender's browser turns the shared secret into an in-memory file named `secret.txt` of type `application/x-fidant-text`. The name and type travel inside the encrypted META, like any file's.
- A shared secret is at most 10,000 UTF-16 code units (`MAX_TEXT_LENGTH`), so at most 30,000 bytes of UTF-8. The field has no `maxlength`, so a longer paste stays whole. While it is over the limit, the field is marked invalid and shows its length against the limit (for example "12,000 of 10,000 characters"), `textFile` refuses it, and no link can be added, so a shared secret is never sent cut.
- The field has `spellcheck=false`, `translate=no`, `writingsuggestions=false`, and `autocomplete`, `autocorrect` and `autocapitalize` set to `off`, which tell the browser to keep its spelling, autocomplete, writing suggestions and translation features off the shared secret.
- The recipient's page treats an offer as a shared secret only when its type is exactly `application/x-fidant-text` and its size is at most 32 KiB (`isTextOffer`, `MAX_TEXT_BYTES`). Anything else is offered as a file.
- An offer of a shared secret shows "<sender's name> sent you a secret" with Show and Decline, and no name, size or type. Show always collects the shared secret in memory (`BlobSink`): never a save dialog, never a download.
- Only after the checks in "Checking on the recipient's side" pass does the page decode the shared secret, as UTF-8, keeping a leading byte order mark (invalid bytes become U+FFFD). It shows it as a text node in a `<pre>`, never parsed as HTML, inside a labelled box with `translate=no` that keyboard users can focus and scroll. No form field holds it, because a browser can save a form field's value with its session. Copy calls `navigator.clipboard.writeText` with the decoded string.
- As for a file: nothing is stored, so the sender's page must stay open; each recipient's link works once; after Decline the link still works.
- The send page has two modes, chosen by a toggle and named in the address: `/send` or `/send/file` for a file, `/send/secret` for a shared secret (in Swedish `/sv/skicka`, `/sv/skicka/fil` and `/sv/skicka/hemlighet`). `/send` names `/send/file` as its canonical address. The old address `/secret` (`/sv/hemlighet`) redirects to `/send/secret` (`/sv/skicka/hemlighet`), and the older `/send?mode=secret` and `/send?mode=file` open their mode, after which the page changes its address to the new one. Loading `/send/secret`, `/secret` or `/send?mode=secret` (in Swedish `/sv/skicka/hemlighet`, `/sv/hemlighet` or `/sv/skicka?mode=secret`) from the server (typing its address, a reload, a bookmark or a link from elsewhere) is an HTTP request for that address, so the server can see that someone opened the send page in secret mode. Each mode, when first shown, opens its own `/signal` WebSocket and sends `host` with its links, and switching to secret mode inside the app opens that connection too, with no page request. The server never gets the shared secret or its length, and a signaling connection doesn't say which mode opened it, but after a full load of `/send/secret` (`/sv/skicka/hemlighet`) the server can tie the connection that follows from the same address to the visit, and infer that this visitor shares a secret and with how many links. A full load of any other page can give away that the visitor shares a secret too. Each mode connects when it is first shown and stays connected while the tab is open, so two sender connections open at once from the same address, with no page request between them, most likely mean the visitor opened both modes in one tab; after a full load of `/send` or `/send/file` (`/sv/skicka` or `/sv/skicka/fil`), the second connection comes from secret mode. Neither the server nor Caddy logs page requests.

## How the file travels

`apps/web/src/lib/peer.ts`, `apps/server/src/turn.ts`, `apps/server/src/relays.ts`, `apps/server/relays.json`, `apps/infra/relay/install.sh`, `apps/infra/box/turnserver.conf`, `apps/infra/box/user-data.sh`, `docs/decisions/0007-turn-relay.md`, `docs/decisions/0010-turn-tls-443.md`, `docs/decisions/0015-relay-switch.md`, `docs/decisions/0019-relay-only-as-fallback.md`

WebRTC tries the paths in this order, and the sender's page shows which one each connection took:

| Path     | Meaning                                                                                                      | Who sees the encrypted traffic |
| -------- | ------------------------------------------------------------------------------------------------------------ | ------------------------------ |
| `direct` | the browsers reach each other's local addresses                                                              | the networks between them      |
| `stun`   | through public addresses learned from our STUN service                                                       | the networks between them      |
| `relay`  | through our TURN relay, added when nothing has connected 3 s after the sender applies the recipient's answer | the networks and our relay     |

- The browsers start with only the `stun:` URLs, so they try `direct` and `stun` without the relay. Only when the sender allows the relay, a relay is up and nothing has connected 3 s after the sender applied the recipient's answer do they add the relay (see "Connecting the two browsers"). ICE then tries every route again, the relay included, and can still pick a direct one.
- A transfer that needs the relay therefore starts about 3 s later. A direct route that hasn't connected 3 s after the sender applied the recipient's answer, for example on a network that loses many packets, gets the relay added and may then end up on the relay.
- The `same network` row of `apps/e2e/tests/networks.spec.ts` checks `direct` on one simulated network: the browsers pick a pair of local addresses, and every IP packet that crosses the network's edge during the test is TCP to the server's 443 or a STUN Binding message to coturn, apart from link-scope IPv6 multicast such as router solicitations, which stays on the link. The `technical` text on `/how` says so.
- On any path each browser sees the other's IP address, like on a video call. STUN sees each browser's address for the binding request, and no file data passes through it. The two browsers' requests reach it about one signaling hop apart, so it can usually tell which two addresses belong together, even when the relay isn't added.
- Relay credentials are minted by the server for each `joined`, so when a pairing starts and each time its recipient joins again after a drop, and sent only to the two paired sockets: the username is an expiry time 5 minutes ahead and the credential is HMAC-SHA1 of it under the relay's secret, which the server and that relay hold. Code that runs as the app's user on the app box can also work it out (see "The relay box"). The expiry limits starting a relay connection, not how long it may run.
- The server hands browsers the URLs of the first relay in `apps/server/relays.json` that is up (see "The relay box"). Today that is the relay box: `stun:sto.relay.fidant.se:3478`, `turn:sto.relay.fidant.se:3478?transport=udp` and `turns:sto.relay.fidant.se:443?transport=tcp`. So browsers reach coturn over UDP on port 3478, or over TLS on TCP port 443, which networks that allow only web traffic still let through. coturn also accepts plain TCP and TLS on 3478, but no URL names them (FID-125). Its other ports (3479 and TLS on 444) are closed by both firewalls. `sto.relay.fidant.se` has only an IPv4 address, so browsers reach the relay over IPv4 only.
- coturn forwards only over UDP (`no-tcp-relay`), and only from its box's private IPv4 address (`relay-ip`), so relayed addresses are IPv4 only. It refuses to forward to other machines on private, loopback, link-local and other internal ranges (`denied-peer-ip`). The accepted exception is that relay clients can reach UDP services on the relay's own box, at its private and public IPv4 address (`docs/decisions/0007-turn-relay.md`, Consequences). It also caps concurrent allocations (`total-quota=200`), and writes no log (`log-file=/dev/null`). The traffic it carries is DTLS and AES-GCM; on 443 it is wrapped in TURN's TLS as well.
- The relay forwards encrypted packets. It can't decrypt them and doesn't store them.

### The fallback relay on the box

Without a relay list, the server hands out the box's own coturn instead, from `TURN_URLS`: `stun:turn.fidant.se:3478`, `turn:turn.fidant.se:3478?transport=udp` and `turns:turn.fidant.se:443?transport=tcp`, plus a `stun:` URL with the box's IPv6 address when it has one. It has the same settings as above. It differs in two ways:

- On 443, HAProxy reads only the TLS server name and ALPN. It passes connections for `turn.fidant.se` to coturn's TLS listener without decrypting them, except Let's Encrypt's `acme-tls/1` checks, which go to Caddy; coturn holds that name's key, a copy of Caddy's Let's Encrypt certificate. coturn sees such a connection as coming from 127.0.0.1, though the peer addresses in it still name the browsers.
- Its other TLS ports (3479, 5349, 5350) are closed by the firewall.

FID-264 takes it off the box (planned).

### The relay box

`apps/infra/relay/install.sh`, `apps/infra/src/relay.ts`, `apps/server/src/relays.ts`, `apps/server/src/relay-secret.ts`, `apps/server/src/turn-check.ts`, `apps/infra/src/relay-cap/cap.mts`, `docs/decisions/0013-relay-service.md`, `docs/decisions/0015-relay-switch.md`, `docs/decisions/0021-relay-cost-cap.md`

The relay is its own service, so that relays can run on any Ubuntu server and in more than one place. The first is a second Lightsail box in Stockholm, set up by `install.sh`, and it carries relayed transfers while the server has a relay list.

- It runs coturn with the settings above, on UDP and TCP 3478, and with TLS on TCP 443 directly, with its own Let's Encrypt certificate for `sto.relay.fidant.se`. No HAProxy sits in front of it, so it sees real client addresses on TLS too.
- At install it makes an RSA key pair. The private key never leaves the box. The server trusts only the public keys in its relay list, `apps/server/relays.json`, which changes only through a pull request that the `maintainers` team must approve (repository admins can bypass that rule).
- The server derives each relay's secret from one master: HMAC-SHA256 of the relay's ID under it. The master is 32 random bytes in `/var/lib/fidant/relay-master` on the box, mode 0600. The server makes it at its first start and keeps it through deploys and reboots. Anything that runs as the app's user can read it, a deploy's build steps included. `FidantSignal`'s task, serving no visitor until the cutover, gets a master of its own from AWS's secret store instead (see "Where traces are kept"). Nothing logs the master or a relay's secret.
- Every minute the relay asks the server for its secret at `https://fidant.se/relay-secret/sto`. The answer is the secret sealed to the relay's public key (RSA-OAEP with SHA-256, `sealRelaySecret`), so anyone can ask but only that relay can open it.
- A new secret reaches coturn through coturn's own SQLite file, without a restart, so relayed transfers in progress keep running. The previous secret stays valid for 24 hours after a change, unless a second change ends it sooner, and longer while no new answer arrives.
- At startup and then every 60 seconds the server checks each relay with a real TURN allocation from the box, under a username marked `probe`, and releases it at once. A relay counts as up once a check passes, and as down before that and after two failed checks in a row. `joined` carries the first relay in the list that is up. When none is, it carries only the first relay's `stun:` URL, so browsers can still learn their public address while the relay answers STUN, but get no relay. `/relay-status` shows which relays are up, to anyone. `FidantSignal`'s task, serving no visitor until the cutover, checks the relays the same way from its own AWS address, with credentials from its own master, which no relay holds yet, so its checks fail and it shows every relay as down.
- When `apps/server/relays.json` is `[]`, or a drop-in on the box turns the list off (`RELAYS_FILE` set but empty, see the runbook in `docs/decisions/0015-relay-switch.md`), the server has no relay list and uses the fallback relay above. Without `TURN_URLS` as well, it hands out only the `stun:` URLs in `STUN_URLS`, if set, with no credentials, so browsers learn their public address but get no relay. fidant.se sets none.
- A cap stops the relay once its estimated cost for the month reaches a budget (`cap.mts`, `docs/decisions/0021-relay-cost-cap.md`). Every 5 minutes a Lambda reads the bytes in and the bytes out of the app box and the relay box since the 1st (UTC), and estimates the month's overage bill as if all inbound traffic came first, the most expensive order. Inbound traffic alone can't close the relay, apart from a replaced box's count carried over from the earlier byte cap: the estimate is at most the month's outbound at 0.09 USD/GB, and the Lambda keeps a carried-over count as outbound. Once about 222 GB has gone out in a month, inbound traffic can close the relay too, because the estimate counts inbound first: with that much out, about 4.22 TB of traffic in and out, 222 GB past the boxes' 4 TB pooled allowance, reaches 20 USD. At 20 USD it closes the relay ports on both boxes until the 1st (UTC), unless we open them again sooner, for example by raising the budget. Relayed transfers in progress then stop, apart from those using TURN over TLS through the app box's 443, which the site offers only while the relay list is turned off (0021), and the server's check marks the relay down. STUN closes with it, so new pairings get no public address from our STUN service and connect only where they can without it, for example on the same local network. Direct transfers already running and the site keep working. Anyone can close the relay and STUN this way, a stranger with no link included, and again each month: the Lambda counts all traffic through both boxes, so loading the site's pages in a loop, or relaying to themselves with the credentials from pairing with themselves (`docs/decisions/0006-signaling-limits-and-turn-credentials.md`), reaches the budget like any other traffic. Of the traffic, the Lambda reads only each box's byte counts. It keeps the month's totals per box and logs the combined totals every run (see "Where traces are kept").
- What the relay box sees, keeps and logs is under "What the server and relay see, keep and log".

### Refusing the relay

`docs/decisions/0008-relay-opt-out.md`, `docs/decisions/0024-safety-number-buttons.md`

The send page has "Use our relay if needed" under "Connection options", on by default, for that send only.

- When it is off, the server mints no TURN credential and `joined` carries only the `stun:` URLs, so the relay is never added. An unmodified browser can't use our relay.
- The sender's page enforces its own choice as well: with the box unticked it keeps only the `stun:` URLs from `joined`, without credentials, and treats the attempt as refused, whatever `turn` the server sent. It does the same at each repeated `joined` of an attempt, and the choice at the latest `joined` replaces the one it stored, so a sender who changes the box during a transfer is judged by the new choice from the next recovery on.
- Backstop: if the sender's selected candidate pair still reads `relay` on a refused attempt, the sender ends the attempt and reports `failed`. It runs after the channel opens, so INIT and META may have passed; file data only flows after ACCEPT. It runs again each time the sender's page reads the path after a recovery, which it does only when its own connection had left `connected` (see "Recovering a dropped route"); by then file data may have flowed, through the relay too if the sender allowed it at an earlier `joined`. It is best effort: the remote candidate's type is what the recipient's browser declares, so a modified recipient can hide its relay (see Limit).
- Limit: a modified recipient can route its own side through our relay with credentials from another pairing, or through any public TURN server. That recipient holds the key anyway. The choice decides which infrastructure carries the encrypted traffic, not who can read the file.

## Several recipients and one-time links

`apps/web/src/lib/sender-state.ts`

- One send can go to up to 256 recipients (`MAX_LINKS`). Each has their own link, key, connection and transfer.
- A link is used only after a matching RECEIPT, which a modified recipient page can send without taking any CHUNK (see step 6 of "The transfer"). A later join on it is refused with `used`. A second page on a link that is already connected is refused with `busy`, and so is every join past the link's 10 pairings in a 30-second window, until the window ends. The recipient's own repeated join during a transfer counts toward the 10; refused past them, it keeps its binding and its transfer.
- Until then the link can be opened again: after a decline, a dropped connection, a setup timeout (20 s), a checksum mismatch, a safety number that didn't match or wasn't confirmed in 5 minutes or, for a shared secret, a connection too small to carry it in one chunk. Each attempt has a new transfer ID and a new attempt ID, and so a new file key. After a dropped connection, the recipient's "Try again" in the same page continues a file where it stopped if it can (see "Continuing after a drop", which says when it can't). A link with the safety number on stops working after 5 attempts that ended before both people confirmed (see "The safety number").
- Nothing is stored, so a link works only while the sender's page is open. When the sender's socket closes, the server forgets its links, within a minute at most (heartbeat every 30 s).

## Emailed links

`apps/server/src/signaling.ts`, `apps/server/src/mail.ts`, `apps/web/src/send/SendPage.tsx`, `apps/web/src/receive/ReceivePage.tsx`, `docs/decisions/0012-email-recipients.md`, `docs/decisions/0030-email-off-until-verified-transfers.md`

Email is off: no deployment sets `MAIL_ENABLED=1`, so no server sends mail and no send page offers the email field, and the site's pages don't describe emailed links (0030). This section describes the code, which stays for verified transfers.

The sender can give a recipient an email address, on `/send/file` for a file and on `/send/secret` for a shared secret. It is opt-in: the address field appears only after the sender ticks "Email the link for me (less private)", which is off on every page load, and ticking it first shows what emailing costs (our server and the mail service see the key, the link stays in the mailbox, and our server could sit in the middle, which a link with a safety number shows). An emailed recipient gets the safety number by default. Fidant then emails that recipient their link, and the recipient's browser can connect only after they enter a one-time code sent to the same address. This is the one case where a link's secret leaves the browser: our server and the mail service see it. Recipients without an address work as described above.

### Registering an emailed link

```
server → sender    hello {mail: true}
sender → server    host {links, turn}                      the new link included
sender → server    email {link, to, secret, from, lang}    once per link
server → mail      notice to `to` with <PUBLIC_ORIGIN>/r/<link ID>#e.<value>.<secret>
server → sender    email {link, status, mark}              sent or failed, with the value
```

- Adding a recipient with an address hosts the link as usual, then sends one `email` message with the link ID, the address, the link's secret, the name the sender typed for themselves and the page language. `host` carries only link IDs, never any of these.
- The protocol parser checks every field first: a valid link ID; a secret of exactly the link secret's form (43 base64url characters that decode to 32 bytes); an address that `<input type="email">` accepts, at most 254 characters; a typed name that passes META's rule above, at most 100 characters; and `lang` `sv` or `en`.
- The server answers `wrong-role` to a recipient's socket. It answers `failed` (naming the link, no mark) when the socket doesn't host the link, when it has no mail service, or when the link has already had an `email` or a guest while hosted, and `limit` when a notice limit is reached. None of these sends mail or changes a binding. But each comes after the `email` message gave the server the link's secret, so the page never offers that link: it gives the recipient a new link (new link ID and secret), sends `host` without the old link ID and with the new one, and ends any join on the old link with `refuse` `unknown`. Only when the page's own socket was closed, so it sent nothing and answers `failed` itself, does it keep the first link.
- Otherwise the server picks a random value for this registration (16 bytes from `randomBytes`, base64url), never derived from the link's secret and never chosen by a client, and binds the link to the address, the language and the value. It then makes one attempt to hand the notice to the mail service, bounded by nodemailer's timeouts (10 s to connect, 10 s for the greeting, 20 s of silence). A notice the mail service doesn't take is never queued or retried.
- The link in the notice is built from the configured `PUBLIC_ORIGIN`, never from the request, so the server can only email links to its own site.
- The link's secret and the typed name exist on the server only in that send attempt, until it ends. They are never stored or logged.
- The reply to the sender carries the value, never the link's secret: `sent`, or `failed` if the attempt failed or timed out. A failed notice leaves the link email-bound, because a timed-out notice may still arrive. To send again, the sender removes the recipient and adds them again, which makes a new link.
- The sender's card offers no link until the reply arrives. With a value, the page builds the same marked link from the link's secret it already has and shows and copies only that. After a refusal without a value, it offers the new plain link that replaced the one the server saw, and a later join on the old link ID gets `refused: unknown`.
- The notice is plain text, from `MAIL_FROM` to that one address, with no Reply-To. Its subject names neither the sender nor the file. Its body has the typed name marked as not verified ("Someone" when it is empty) and the link, and says "a file or a secret" for both. No email names the file, gives its size or type, or says whether the link carries a file or a shared secret.

### Opening an emailed link

```
recipient → server     gate {link, mark}
server    → recipient  gate {link, to}                  the masked address, or ""
recipient → server     send-code {link, mark}
server    → mail       code email to the bound address
server    → recipient  code {link, result}              sent, wait, limit or failed
server    → sender     email {link, status: verifying}
recipient → server     code {link, code, mark}
server    → recipient  token {link, token}              or code {link, result: wrong, expired or tries}
server    → sender     email {link, status: verified}
recipient → server     join {link, attempt, token}
```

- The recipient page reads the value from `#e.<value>.<secret>` and sends `gate` with it before the first `join` on every signaling socket, rejoins and reloads included, except a socket that takes its attempt back with `resume` (see "Taking an attempt back on a new socket"), which sends no `gate` and no first `join`. A `join` it sends again on the same socket, after `starting` or when its open connection drops, follows no new `gate`; it carries the token, and the server checks it. The server answers with the masked address (`a***@example.se`) only when the value matches the link's current binding. Any other `gate` (no value, a wrong value, a link that is not email-bound or unknown) gets `to: ""`, the same answer as for a plain link. So someone with only the link ID can't see the masked address or cause code emails.
- For a marked link, `to: ""` means the binding is gone: the page joins nothing and says the link no longer works (`unbound`).
- `send-code` and `code` carry the value too. With a wrong one, `send-code` answers `failed` and `code` answers `expired`, and no code is sent or checked. A code is 6 digits from `randomInt`, works for 10 minutes or until the fifth wrong try, and replaces any earlier code for the link. The server compares it with `timingSafeEqual`. A right code gets a token of 16 random bytes, base64url.
- The page keeps the token in that tab's `sessionStorage` under `token:<link ID>` and joins with it. A reload or a rejoin in the same tab reuses it. Another tab or browser needs its own code, except a tab the browser copies sessionStorage into, such as a duplicated tab.
- The server refuses a `join` on an email-bound link without a token its current binding issued, and a `join` that carries a token on any other link. It logs `refused` with reason `unverified` and answers `gate {link, to: ""}`, never the masked address. The page then drops its token and, for a marked link, asks `gate` again, unless its data channel is open: then the `gate` can only answer a repeated `join`, and the page ignores it.
- A rejoin keeps the code field. A `failed` or `expired` code result makes the page ask `gate` again, so a binding that is gone ends as "this link no longer works".
- The page shows no sender name before the code. As for any link, the recipient reads it from META.

### What the server keeps, and limits

- While the sender's page hosts the link, the server holds in memory the address, the language, the value, the latest code with its expiry and tries, when the link's codes went out, the tokens, and whether the link already had its `email` or a guest.
- Unhosting the link (a `host` without it, which is what removing the recipient sends, or the sender's socket closing) drops all of it, and so does a server restart. One exception: when the sender's socket ends with no close frame while the link's attempt is armed, the server holds the binding for up to 30 s, and a takeover by the sender's new socket keeps it (see "Taking an attempt back on a new socket"). The emailed link then connects to nothing, even if someone hosts the same link ID again as a plain link.
- The limits are `LIMITS` and the code constants in `apps/server/src/signaling.ts`:

| Limit                                             | Value                                    |
| ------------------------------------------------- | ---------------------------------------- |
| Notices from one sender socket                    | 20 an hour                               |
| Notices from one client address (IPv6 by its /48) | 50 an hour                               |
| Notices to one email address                      | 5 an hour                                |
| Notices from the whole server                     | 500 an hour                              |
| Codes for one link                                | 5 while it is hosted                     |
| Time between two codes for one link               | 30 s                                     |
| Codes asked for by one client address (as above)  | 5 an hour                                |
| Codes to one email address                        | 10 an hour                               |
| Codes from the whole server                       | 500 an hour                              |
| A code's life                                     | 10 minutes, or until the fifth wrong try |

- The limits per email address and for the whole server can be used up by anyone, a stranger with no link included: they can stop notices or codes to one address, or all of them, for up to an hour, and a sender who gets `limit` can tell that the notice limit was reached. A refused code counts against nothing, and a client's own limit on codes (5) is below the address's (10), so one client can't use up an address's codes on its own (0016).
- The counters per email address and per client address hold only send times, under an HMAC-SHA-256 of the lowercased address or the client address with a 32-byte random key made when the server starts. The two counters for the whole server hold only send times. They outlive the link, stay in memory for at most an hour and are pruned on the heartbeat. The per-socket count lives on the socket and goes with it.

### The mail service

- The server sends mail over SMTP with nodemailer only when `MAIL_ENABLED` is `1` and `MAIL_SMTP_URL`, `MAIL_FROM` and `PUBLIC_ORIGIN` are all set (`mailService` in `apps/server/src/mail.ts`). Without `MAIL_ENABLED=1` it ignores the mail settings, `MAIL_PASSWORD_FILE` included, and `MAIL_ENABLED=1` without them stops it at start. Without mail `hello` says `mail: false` and every `email` gets `failed`. An SMTP password comes only from the file named by `MAIL_PASSWORD_FILE`, never from the URL. `smtps://` uses TLS from the start, and `smtp://` requires STARTTLS whenever a password is set and for every host except loopback (localhost, 127.0.0.0/8, ::1), and never falls back to plain text. Certificate verification stays on.
- Mail service errors can quote the address, so the server keeps none of them and logs only the outcome.
- Locally, `pnpm e2e` runs Mailpit, which catches every mail and never sends it on, and sets `MAIL_ENABLED=1`. `pnpm start` sends no mail unless those variables are set.
- In production the mail service is Amazon SES in eu-north-1. The box can hold mail settings, but no deployment sets `MAIL_ENABLED=1`, so the server ignores them and fidant.se offers no email field (0030).
- SES stops all sending when the account's bounce rate reaches 2 % or its complaint rate 0.05 %, below the rates at which AWS reviews the account. Every `email` and code then gets `failed` until a maintainer turns sending back on. The alarms read only these rates, never a bounce or complaint itself.

### Who can read an emailed link's key

- Our server, while it builds and sends the notice, and the mail service.
- Anyone who can read the mail in transit, the recipient's mailbox provider for as long as the mail is kept, and link scanners that fetch it. A scanner can't connect without the code.
- Anyone who can read that mailbox, who can also get the code and so the file or shared secret.
- With the key, our server could open that link's sealed setup messages, swap the DTLS fingerprints and sit in the middle of the transfer, or open the link itself and act as the recipient. The code doesn't stop this, because Fidant sends the code. The safety number, which an emailed recipient gets by default, shows the two people when it happens: the recipient's screen shows a different number, or none. Without a safety number, nobody would notice. A sender who doesn't want any of this leaves "Email the link for me (less private)" unticked and passes the link on themselves.

## What stays on the two devices

`apps/web/src/theme.ts`, `apps/web/src/i18n/language.ts`, `apps/web/src/prepaint.js`, `apps/web/src/send/SendPage.tsx`, `apps/web/src/receive/ReceivePage.tsx`, `apps/web/src/lib/notify.ts`, `apps/web/src/lib/favicon.ts`

- Both pages keep the links, keys, transfers and file data only in memory. Fidant writes only two things to storage that outlasts the tab: the chosen theme and language, in `localStorage`. Two more things can outlast the tab: the tab's status icon, which the browser keeps with its history, and, outside the browser's storage, a delivery notification, if the sender allowed them (both below).
- Sender: the file is read from where it is and copied nowhere else. A shared secret is typed into a `<textarea>`, whose value a browser can save with its session. A link the sender copies is on their clipboard.
- Sender, only while the browser allows notifications for the site, which the "Notify me" button asks for: each delivery that happens while the page is out of focus shows a browser notification (`notify.ts`). The operating system shows it and can keep it in its notification list, and some systems mirror that list to other devices. Its text is fixed words that say whether a file or a secret was sent, plus how many links have delivered out of how many; the notification for the delivery that completes every link has no counts. It never holds a file name, a recipient's name, a link or a key. The browser remembers the permission for the site until the sender takes it back in the browser's settings.
- Recipient: the file is where they saved it (see "Checking on the recipient's side"). After a lost connection, the part of a file that arrived stays in page memory, or in the open file from the save dialog, until "Try again" continues or discards it, the page shows another ending, or the tab closes or reloads. What the browser does with an unfinished save dialog file when the tab closes is not tested yet (see "Continuing after a drop"). A shared secret is only in the page's memory until copied, then also on the clipboard (see "What Fidant doesn't protect against"). For an emailed link, the token stays in that tab's `sessionStorage` (see "Opening an emailed link").
- Both: the browser's history keeps every address it opened, so the recipient's history holds the link with its secret, like any address. The link is refused once its file is delivered and works only while the sender's page is open.
- Both: the tab's icon shows the transfer's status (`apps/web/src/lib/favicon.ts`): a green dot while a transfer is open, a green check once it is done, a red stop sign on the screen that asks for a secure connection, the logo otherwise. Browsers keep the icon of each visited page in their own favicon store, beside history, so the history entry of each page the tab showed while it had that status, usually `/send`, `/secret` or `/r/<link ID>` but also any other page of the site opened in that tab, can keep the dot or the check after the tab closes. That shows a transfer was open, or that it arrived, to anyone who can read the browser's profile on that device. It holds no file name, content, key or recipient. On an address without HTTPS, `/send`, `/secret` and `/r/<link ID>` show only that screen, and its stop sign can stay beside that page's history entry in the same way and shows only that the page was opened without a secure connection. Chromium, checked by hand on 2026-11-26 in a fresh profile by reading its `Favicons` database after a test page changed its icon (FID-327; no automated test covers it), keeps only the icon's last state, as small bitmaps, against the full address, fragment included, so for a link the favicon store holds the link with its secret beside history, until history is cleared. Firefox, Safari and private windows are not tested yet.

## The web app and the server

`apps/server/src/server.ts`, `apps/server/src/relays.ts`, `apps/server/src/settings.ts`, `apps/server/Dockerfile`, `apps/server/entrypoint.sh`, `apps/web/src/lib/signaling-list.ts`, `apps/web/src/main.tsx`, `apps/web/src/prerender.tsx`, `apps/web/src/prepaint.js`, `apps/web/src/i18n/language.ts`, `apps/web/src/i18n/preview.ts`, `apps/web/vite.config.ts`, `apps/infra/box/user-data.sh`, `apps/infra/edge/site.js`

- HTTPS only, with `Strict-Transport-Security` (Caddy, Let's Encrypt). Send and receive refuse to run outside a secure context.
- HAProxy holds TCP 443 and passes every connection not for `turn.fidant.se` to Caddy on port 8444, without decrypting it. It adds a PROXY protocol header, which Caddy accepts only from 127.0.0.1, so Caddy and the server still see the real client address (`docs/decisions/0010-turn-tls-443.md`). HAProxy logs nothing and stores nothing on disk; it holds only addresses and connection counts in memory, for its per-source cap.
- `Content-Security-Policy: default-src 'self'; img-src 'self' data:; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`: code, styles, fonts and connections only from our own origin, images from our own origin or inline in the page (`data:`, which the tab's icon uses, so that a change of a transfer's status asks the server for nothing), and no framing. `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`.
- No cookies, no third-party scripts, fonts or trackers.
- Static files are served only from the build directory; path traversal is refused.
- Each public page is a file the build renders from the app (`apps/web/src/prerender.tsx`), English at `/...` and Swedish at `/sv/...` under Swedish names (`/sv/sakerhet` is `/security`; the list is in `apps/web/src/i18n/language.ts`), so the path of a public page names the page's language. When the visitor has chosen a language, the path tells the server that choice, which can differ from the browser's language. Its head holds only fixed text: the page's title and description, its link preview (Open Graph tags), and its canonical and hreflang links. A path under `/r/` is not a public page: it has one path for both languages and gets one of two copies of `index.html`, picked by whether `Accept-Language` starts with `sv`, with `Vary: Accept-Language` and `X-Robots-Tag: noindex`; its link preview says something was sent to you. Files with an extension other than `.html` are served from the build directory, and a missing one gets an empty 404. A trailing slash on a page's path, the old `/technical`, and the old `/secret` and `/sv/hemlighet` (to `/send/secret` and `/sv/skicka/hemlighet`) get a permanent redirect within the site that keeps the query; any other path (no extension, or `.html`) gets the 404 page, the Swedish one under `/sv`. Like a browser, a preview fetcher sends us the path but never the part after `#`.
- A script in the head of each public page (`apps/web/src/prepaint.js`) applies the stored theme before the page paints and, on an English page, opens the Swedish one when the stored choice is Swedish, or when nothing is stored and the browser language is. Receive pages don't load it.
- The WebSocket accepts upgrades only on `/signal`, and refuses one whose `Origin` is another site. Our site is the host the request names and, when `PUBLIC_ORIGIN` is set, that origin too, so the server can run on another name than the pages.
- The per-address limits count a client by the address its connection comes from. When that is a proxy the server trusts, they count the rightmost `X-Forwarded-For` entry instead, the one that proxy wrote. When such a proxy passes on more than one `X-Forwarded-For` line, the rightmost entry could be one the client wrote, so the server refuses the upgrade with 400 before it counts any address, and logs `upgrade-rejected` with reason `forwarded`. One line with several entries still counts its rightmost entry. An entry that is not a plain address, such as one with a port, is ignored, and the connection then counts against the proxy's own address. A proxy on the same host is always trusted, which is how the server sees addresses behind Caddy. `TRUSTED_PROXIES` names address ranges that are trusted as well. fidant.se sets none.
- With `SIGNALING_ONLY=1` the server serves no pages. It answers `/signal` and the two relay routes, and 404 for every other path. `apps/server/Dockerfile` builds an image that runs the server this way, with no web build inside (`docs/decisions/0023-hosting-off-the-box.md`). Its entrypoint writes the relay master from `RELAY_MASTER` to the file `RELAY_MASTER_FILE` names, mode 0600, and starts the server without that variable. Without `RELAY_MASTER` it stops before the server starts, so the server in the image never makes a master of its own. fidant.se neither sets `SIGNALING_ONLY` nor runs the image.
- The web app opens its WebSocket to the host it was loaded from. A build made with `SIGNALS_FILE` takes the address from the first entry of that list instead; `apps/web/signals.json` names `wss://sto.signal.fidant.se/signal`. The build that fidant.se serves is made without it. Pages from a build made with it need a `Content-Security-Policy` that allows that address. This server's allows connections only to its own origin, so it cannot serve them.
- `apps/infra/edge/site.js`, a CloudFront function, applies the same page rule with the headers above and `Strict-Transport-Security`, and a `Content-Security-Policy` whose `connect-src` adds `wss://sto.signal.fidant.se`, so it can serve such a build. It redirects every other host name to `https://fidant.se` with the same path and query. Before any other rule, the guard below included, a path longer than 128 characters, not counting the query, gets the function's empty 414 with the three headers and HSTS, on every host, because at 256 characters the costliest of the three paths measured took 52 % of the function's time budget, over the trial's limit of 50. The function uses no regular expression, because CloudFront stopped it on regex limits with paths of 512 characters in the part-3 trial. A missing file it passes on gets the bucket's own 404, without the headers, as does any other answer of 400 or more from the bucket. No page read states what CloudFront's own errors and its http-to-https redirect carry. In the part-3 trial in `docs/decisions/0023-hosting-off-the-box.md`, on 2026-11-26, its 403 to a POST and its 301 to https carried none of the three headers and no HSTS. On `fidant.se`'s distribution it also runs as viewer request on `/relay-secret/*`, which CloudFront passes on uncached to `sto.signal.fidant.se`: the function guards any URI that contains `/relay-secret/` once its escapes are decoded and its backslashes read as slashes, because AWS gives no order for the steps with which CloudFront normalises a path before it matches a behaviour (`docs/decisions/0023-hosting-off-the-box.md` cites the page). A request passes unchanged only when its URI as sent is exactly `/relay-secret/<id>` with an id of the server's rule `^[a-z][a-z0-9]{1,15}$`, and everything else the guard sees gets the function's empty 404 with the three headers and HSTS, instead of what the page rule would give it, so a path elsewhere that merely contains `/relay-secret/`, such as `/how/relay-secret/x`, gets that empty 404, not the 404 page. It answers there on every name the distribution serves, redirecting other host names to `https://fidant.se` as everywhere. A passed request gets the signaling server's own answer, with its headers and no HSTS, the load balancer's own error, which carries none of them, or CloudFront's own error, such as its 502 when it cannot connect to the origin, whose headers no page read states. No visitor reaches it before the cutover (`docs/decisions/0023-hosting-off-the-box.md`).
- Two routes serve the relays, with `Cache-Control: no-store` and the headers above. They take only GET and HEAD and need no authentication. `/relay-status` answers JSON with each relay's ID and whether it is up, such as `[{"id":"sto","up":true}]`, or `[]` without a relay list. `/relay-secret/<id>` answers a relay's sealed secret as one line of text (see "The relay box"). Any other path under them gets 404.
- Limits: HAProxy closes a source's 129th concurrent connection on 443 (a source is an IPv4 address or an IPv6 /64) and an idle connection after 2 minutes, or after 1 hour on the path to the fallback relay. The server allows 1,000 sockets, 32 per client address (an IPv6 address counts by its /64), 1,000 messages per socket per 30-second window, 10 pairings per link per window, a bound recipient's repeated join counting as one (more joins are refused as `busy`, so a guest who joins and is refused in a loop on one link cannot spend the sender's message limit; one who holds about 100 of a sender's links still could; a recipient bound on each link, whose every repeated join costs the sender's socket a `restart-offer` and new candidates, roughly 5 to 10 messages by estimate, could on roughly 7 to 20; an honest recipient pairs at most 5 times to open an attempt, then once or twice per route that drops after it), 256 links per sender, 16,384 characters per relayed setup message, 256 KiB queued to a socket that isn't reading before relays to it are dropped, 512 KiB before the socket is ended, and the email and code limits under "Emailed links". The server closes an HTTP connection that has been idle for 6 seconds and gives a request 60 seconds to send its headers. With `HTTP_KEEP_ALIVE_MS` set, both are 1 second longer than its value. fidant.se sets none.

The sealed `data` of a `relay` message is a `commit`, an `offer`, an `answer`, an `ice` candidate (each page's first is its version marker) or, when the relay is added or a dropped route is recovered, a `restart-offer` or a `restart-answer` (`apps/web/src/lib/peer.ts`).

A `join` can come again from the socket the server has already bound to that link, with the same attempt ID: the recipient's page sends it when its open connection drops (see "Recovering a dropped route"). The server checks its token again, counts it toward the link's pairings and answers with `joined` to both pages, or with `refused` (`busy`) or `gate`, which leave the binding as it is. So one attempt can get more than one `joined`, each with ICE servers and `turn` made at that moment. Any other `join` on a bound socket gets `error` with `already-joined`. After a takeover, the repeated `join` comes from the socket that took the recipient's side, which the server has bound in the old one's place. Once its data channel is open, the recipient's page ignores `refused` with `busy`, any `refused` after `host-gone`, `gate` and `error`.

`resume` goes both ways with the same fields. The server sends it with a token when it arms an attempt and to answer a page's `resume`, and without one to refuse it. The page sends it first on a new socket, with the token it holds (see "Taking an attempt back on a new socket").

### Every server log line

Written as one JSON line, `{event, ...fields}`, to stdout and from there to the journal (deleted after 30 days). `FidantSignal`'s task, serving no visitor until the cutover, writes the same lines to its CloudWatch log group instead, kept 14 days, typically 17 at most. `LogEvent` and `LogFields` in `packages/protocol/src/signaling.ts` are the only allowed shape; /privacy lists them from the same type.

Fields: `link` (first 6 characters of a link ID), `links` (a count), `bytes` (a message size), `reason`, `code` (an error code), `port`, `path` (the route).

There is one `joined` line for each `joined` the server sends, so a recipient's repeated join after a dropped route logs `joined` again for the same link, or `refused` with `busy` past the link's 10 pairings, or `refused` with `unverified` when its token doesn't fit. A repeated join that crosses the sender's refusal logs `joined` and then the sender's `refused` with `drop` for that attempt. No event or field says that a join was a repeated one, but two `joined` lines for one link with no `left`, `refused` or `host-gone` line between them show it. The `path` line is written once per connection and not again after a recovery.

A page that takes its attempt back on a new socket logs `resumed`, or `resume-refused` when the server refuses (see "Taking an attempt back on a new socket"). A takeover of the sender's side after the recipient asked again logs `joined`, or `refused` with `busy` past the link's 10 pairings. The server logs nothing when it starts to hold a side. When a hold runs out, that side's `host-gone` or `left` line comes up to 30 s after its socket closed, and when both sides were held and the sender's hold runs out first, the log shows `left` and no `host-gone`. The sender's page sends `host` again when its connection reports `disconnected`: while another socket still holds one of its links, each such `host` logs `error` with `already-hosted` again.

## What Fidant doesn't protect against

- **The link is the key.** Anyone who gets a link can open the file or shared secret behind it until the link is used. A link Fidant emails also needs a code sent to the same address, so it opens for anyone who can read that mailbox. Send each link only to its recipient, over a channel you trust.
- **Emailed links.** Our server, the mail service and the recipient's mailbox see the key. Our server could sit in the middle of that transfer; with the safety number on, the two people see different numbers and nothing about the file goes, so this is a gap only for an emailed link sent without a safety number. See "Emailed links" and "The safety number".
- **The served code.** The browser runs the code our server sends. A server that sent different code could read files, and could skip the safety number. The code is public, but a browser can't yet check that what it received matches it.
- **Unverified sender name.** Typed by the sender.
- **Metadata.** The other browser sees your IP address. The networks and, on the relay path, our relay see both IP addresses, timing and the rough size. Our server sees both IP addresses, which recipient connects to which sender, when, and how many recipients a sender has, and for an emailed link the recipient's email address. When a recipient's page asks again after a dropped route, it also sees that this transfer's connection dropped, and when. So it learns who sends to whom, though not what, unless it sits in the middle of an emailed link's transfer sent without the safety number.
- **Compromised devices.** Malware on either computer can read the file before encryption or after decryption.
- **Copied secrets.** When the recipient copies a shared secret, it goes to the operating system's clipboard, where clipboard history, cloud clipboard sync and other apps can read it. Once a shared secret has been shown, Fidant can't reach it: it can't take it back or clear it from the recipient's screen, memory or clipboard.
- **No independent audit yet.**

## Planned: verified transfers

Not built. Designed in `docs/decisions/0001-e2e-tests-and-leak-model.md`, `0002-evidence-model.md`, `0003-audit-log.md` and `0004-one-store-dynamodb.md`:

- The recipient signs a receipt with BankID before they can open the file. The receipt text names the file, the one deliberate exception to "no file names on the server".
- The key is split. The server stores one half and releases it only after the receipt is signed.
- Events go to a tamper-evident, hash-chained audit log, anchored with RFC 3161 timestamps, with parties as HMAC references instead of names or personal identity numbers.
